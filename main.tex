\begin{abstract}
Coding agents can implement a requested feature while violating its security contract. We present \tracer{}, a change-informed investigation and repair workflow that connects static-analysis findings to Python symbols, temporal AST edits, and separately recorded development rationale. It grounds diagnoses in current source, uses conditional runtime checks, validates candidate repairs, and preserves repair invariants for subsequent maintenance. Our SusVibes study admits 387 generator attempts and completes 1,548 repair cells with each of two investigators. Primary SAST locations overlap reference-patch symbols in 52/387 attempts (13.4\%), while change-informed plans include such symbols in 366/387 (94.6\%). On 345 shared, eight-arm execution-complete attempts, original SecPass is 68 (19.71\%); the change-informed snapshot configuration reaches 71 with DeepSeek and 70 with Gemini. The rationale-enabled configuration ranks highest for both investigators, reaching 76 (22.03\%) and 75 (21.74\%), while the combined temporal/rationale configuration reaches 74 and 73. Seven development revisions and a stage-level audit identify distinct losses in diagnosis, validation scheduling, and repair completeness. A researcher-run structural-biology case study verifies five component repairs across repositories selected for Barcelona collaborator review. During silent-fix feature evolution, unguarded continuation achieves joint feature and boundary success in 3/5 cases, while persistent security memory with a one-retry gate achieves 5/5. Together, these results characterize the opportunities and engineering requirements of provenance-aware security maintenance.
\end{abstract}

\section{Introduction}
Coding agents navigate repositories, change files, and execute tests through interfaces such as SWE-agent~\cite{sweagent}. Their development traces preserve both the code they changed and explanations of what they intended to accomplish. A passing functional suite can nevertheless leave an implementation with an unsafe input boundary, incomplete validation, or a violated library contract. SusVibes makes this gap observable by evaluating functionality and security separately~\cite{susvibes}. For a team accepting agent-generated changes, the immediate problem is therefore how to review working code before integrating it. A useful intervention must preserve the requested behavior while finding and repairing the omitted security condition. It must also leave enough evidence for a later maintainer to understand why the repair exists.

Static application security testing (SAST) offers reproducible rules, source locations, and flow evidence through CodeQL and Semgrep~\cite{codeql,semgrep}. These findings provide concrete starting points for an investigator, but many relevant implementation changes lie outside warning locations. In our admitted corpus, primary scanner locations overlap reference-patch symbols in 52/387 attempts, whereas a change-informed plan includes a reference symbol in 366/387. That difference makes source selection an important part of the workflow. Once the relevant code is available, its evolution can expose a removed guard, a changed representation, or an asymmetry between related functions. Recorded development rationale adds a second source of questions by describing assumptions about inputs, dependencies, and expected behavior. Connecting these signals to the current implementation creates a richer review process than inspecting the final warning location alone.

\tracer{} organizes that process as change-informed planning, separate provenance channels, guarded investigation, and persistent repair evidence. It maps submitted edits to Python symbols, attaches scanner findings and syntactic relations, and summarizes temporal changes with typed AST differencing. It retrieves recorded rationale separately so an investigator can test a stated assumption without confusing that statement with a source-code fact. A source-bound assessment establishes the proposed invariant gap; when the static evidence remains inconclusive, a bounded runtime check tests the current candidate. The investigator then edits production code and validates the resulting implementation against public functional tests. The resulting repair note records the evidence chain and can be bound to an independently owned boundary check for later maintenance. This makes the security review inspectable at both the repair and continuation stages.

We evaluate the workflow across seven archived coding generators and two security investigators, producing 3,096 v12 repair cells. On 345 cases with complete evaluations in all eight configurations, the rationale-enabled bundle achieves the highest SecPass count with both investigators: 76 for DeepSeek and 75 for Gemini, compared with 68 original successes. The combined temporal/rationale bundle reaches 74 and 73, showing that more context does not automatically improve the final repair. A seven-version development study and a full-cohort investigation funnel explain how evidence availability, supported diagnosis, patch retention, and semantic completeness contribute to these outcomes. We complement the benchmark with a focused study of computational-biology pipelines, where five verified component repairs produce persistent notes and executable boundary checks. Under subsequent feature evolution, memory plus a one-retry gate completes all five requested changes while preserving those checks, compared with three unguarded continuations. Our contributions are the evidence-linked architecture, the completed multi-investigator evaluation, and the engineering analysis that connects repair outcomes to concrete workflow stages.

\section{Background and Motivating Traces}
\label{sec:motivation}
A security review combines evidence with different roles and lifetimes. A scanner warning associates a rule with a source location or reported flow. A code-change descriptor records how a symbol evolved between observed versions. A ReAct-style explanation records what the coding agent said while developing that change~\cite{react}. The investigator uses these inputs to form a hypothesis, which is then checked against the current source or execution. Finally, the benchmark's separate functional and security tests evaluate the retained implementation. This sequence makes the distinction between historical motivation, current diagnosis, and final outcome central to the design.

An RSA development trace illustrates the value of comparing related symbols. Its \code{decrypt} function guards the encoded input length, while \code{verify} initially compares hashes without an analogous signature-length condition. A combined-context investigation follows this asymmetry and adds a length check before converting the signature into an integer. That candidate satisfies the official security evaluation in a diagnostic case where the snapshot configuration does not. A LangChain link-extraction trace exposes a related completeness problem: network-location equality is checked, but scheme equality is omitted from the origin condition. The investigator adds the missing comparison, connecting a local edit to the broader input contract. Both traces show how change evidence can direct a review toward a specific missing condition.

Other traces show why that condition must be checked at the correct boundary. In Wagtail, a label helper produces an intermediate string whose escaping behavior depends on the rendering consumer. An early investigator adds escaping at the producer and introduces double-escaping; requiring consumer inspection later preserves the expected output. In Django's \code{strip_tags}, recorded rationale describes character-reference conversion as desirable, while the tested contract requires preserving relevant text representations. The investigator recognizes the disagreement and changes parser settings and entity handlers, but an incomplete handler repair still fails the security tests. GumTree's structural edit matching~\cite{gumtree} and CoLeFunDa's function-change representations~\cite{colefunda} motivate compact descriptions of such evolving code. In \tracer{}, those descriptions guide the questions asked of the current implementation, while the assessment and validation stages determine whether the proposed repair satisfies its contract.

\subsection{Change-Informed Symbol and Relation Planning}
The planner receives the submitted agent patch, current production source, and scanner output. Changed lines and deletion anchors map to Python functions and classes, with explicit module-level or unavailable mappings when a symbol cannot be resolved. Production filtering removes tests and documentation from the editable target set. Guards, calls, candidate in-file callers, and related changed symbols provide a local structure for review. Scanner flow records retain their rule, source, and position provenance when attached to that structure. The bounded plan prioritizes changed production symbols and preloads a primary target with supporting source, enabling useful review even when no scanner warning overlaps that target. In the admitted corpus, it includes a reference-patch symbol in 366 attempts and its complete body in 329, providing the source context needed for the subsequent diagnosis.

\subsection{Separate Temporal and Rationale Channels}
The temporal representation distinguishes cutoff-bounded Git ancestry from edits reconstructed from an agent trajectory. Each adapter records source identities, transition events, available context, and continuity gaps. Typed Python ASTs are serialized to a pinned GumTree 3.0.0 implementation~\cite{gumtree3}, whose edit scripts identify changes in guards, calls, and relevant expressions. Parent-subtree operations preserve evidence inside wholly added functions even when the matcher emits no separate leaf action. Fragment normalization restores recoverable indentation and surrounding structure before parsing. Per-symbol, operation, and character budgets keep the delivered history bounded, while recording which material was truncated. This representation lets an investigator follow an observed change back to its source rather than treating the repository as an unstructured collection of past snapshots.

Recorded rationale follows a separate retrieval path. The extractor retains original prose with event identities, offsets, hashes, and available path/action/symbol associations. It excludes fenced code from the prose channel so source changes and language remain distinguishable. Queries prioritize assumptions, API expectations, corrections, and explanations linked to the current target. Change and divergence cards connect those excerpts to concrete review questions, such as whether a sibling guard applies to the present input or whether validation occurs during construction. When the investigator cites a historical assumption, its assessment records whether current evidence supports, contradicts, or leaves that assumption unresolved. Rationale can therefore remain useful when a source transition is incomplete, while the two channels keep independent provenance and availability records.

\subsection{Static-First Investigation and Guarded Repair}
The investigation protocol supports reading and searching source, inspecting structure and scanner flows, retrieving rationale, proposing hypotheses, assessing evidence, executing checks, and editing production code. Each hypothesis identifies a target, input or trust boundary, path to a sink or contract, and alleged violated property. A conclusive static assessment quotes the current source and binds the quotation to its location and identity. When evidence remains inconclusive, a bounded Python check follows the static-guidance/dynamic-feedback pattern illustrated by PAGENT~\cite{pagent}. The check records target reachability, ordinary-input behavior, boundary observations, and setup or runtime errors. Class targets are reached when execution enters a method or line within their AST span. Custom CodeQL queries inspect the original candidate database, while runtime checks execute the current edited candidate, making the source version explicit in both forms of evidence.

Edit authorization depends on the boundary under investigation. An HTML producer must be assessed together with its rendering or escaping consumer, because an intermediate string alone can misrepresent the final output contract. An intrinsic input validator can instead be assessed at its public entry point, and preloaded callers count as inspected evidence. A source-bound refutation records the rejecting guard, transformation, or return condition and the argument that it covers the hypothesized input. After support, an edit triggers current-candidate reassessment, applicable check reruns, and public functional validation. Exact-patch validation results can be reused, and the resumed runner provides a final public check for a remaining unvalidated candidate. Finalization retains an accepted patch or preserves the unvalidated buffer separately while evaluating the unchanged output. The saved actions and buffers expose which requirement determined the final candidate.

\subsection{Persistent Evidence and the Portable Interface}
The investigation emits an \code{edit_note.json} containing the retained patch identity, summary, hypotheses, assessments, alert decisions, and source/input/trajectory hashes. Its nested records preserve symbol targets and the historical or rationale evidence used in the review. The maintenance extension adds a repair invariant, exact target-source identity, and a qualified executable boundary check owned outside the proposed edit. A continuation gate resolves the target, verifies the source and check identities, and executes ordinary, feature, and boundary checks against the new proposal. A failing proposal receives bounded feedback; an unsuccessful final proposal leaves the qualified repaired version in place. These records distinguish a proposed change, an accepted feature, and preservation by fallback. Section~\ref{sec:practice} evaluates that lifecycle in computational-biology repositories.

The portable skill exposes the same evidence discipline to an agent or practitioner without depending on benchmark-specific paths. A local wrapper accepts either a bounded Git range or a compatible recorded agent trace and constructs the symbol-level review plan. Installed scanner adapters enrich the plan with findings and reported flows. Available GumTree and rationale adapters attach their own evidence and provenance. The wrapper produces a review bundle and repair-note records that a host agent can consume through its existing execution interface. Source and check identities allow a later invocation to recognize that a reviewed target has changed. This plug-in structure supports incremental adoption in an existing repository workflow while preserving the evidence needed to audit a decision.

\section{Experimental Design and Reproducibility}
\label{sec:design}
\subsection{Research Questions, Inventory, and Admission}
We organize the completed study around four research questions. RQ1 asks how scanner findings and change-informed plans differ in the source they expose for review. RQ2 asks whether the repair workflow improves verified security outcomes while preserving functionality. RQ3 compares the temporal, rationale, and combined input bundles on identical attempts. RQ4 examines where cases are lost between localization and successful repair, and how engineering revisions affect those transitions. An \emph{attempt} is a benchmark task paired with one archived coding-generator output; a \emph{cell} additionally identifies the security investigator and arm. These are retrospective reporting questions for the completed experiments, and repeated generator attempts on the same task are treated as correlated observations.

Table~\ref{tab:inventory} summarizes the source inventory and admission. Seven generators each contribute 186 tasks, giving 1,302 archived attempts and 472 publisher-FuncPass outputs considered during preparation. Of those, 391 become ready under the initial workflow: 59 do not reproduce functional success in that preparation check, 20 lack source, and two have incomplete scans. Four source-only exclusions produce 387 v12 attempts across 118 tasks: three primary Python files do not parse, and one patch has no current production review target. These exclusions occur before v12 investigation. Subsequent terminal-aware evaluation corrects an initial parser that could mistake missing failure counts for completed execution. The historical v6 comparison consequently uses 302 fully matched attempts, while final v12 comparisons use 354 DeepSeek four-arm cases and 345 shared eight-arm cases.

\subsection{Investigators, Inputs, and Experimental Bundles}
The recorded investigators are \path{deepseek/deepseek-v3.2} through \path{siliconflow/fp8} and \path{gemini-3.8-flash} through the native Gemini endpoint. Both configure temperature zero, and Gemini configures LOW thinking. Each v12 cell permits 22 turns under a shared 100,000-byte message setting. All arms receive the functional request, patch-selected current source, scanner context, and the same guarded action protocol. C0 is therefore a change-informed snapshot plus SAST-guided repair configuration. C1 adds temporal AST history, C2 adds recorded rationale, and C3 combines both with linked divergence evidence. The benchmark withholds upstream Git ancestry to avoid revealing masked implementations, so measured temporal evidence comes from the archived post-reference agent trajectory.

The four arms share pinned scanner manifests: Semgrep CE 1.101.0 with Python rules at commit \code{495df89c}, and CodeQL 2.20.0 with Python queries 1.3.4 and the security-extended suite. The Semgrep directory includes correctness and maintainability rules alongside security checks. Scans use an oracle-free source export, after which prompt planning scopes findings to changed files and at most twelve groups. The overlap audit retains the full scanner output rather than only the delivered warning subset. Scan diagnostics remain recorded: 23 Semgrep runs contain 37 diagnostics, including 25 timeouts, and CodeQL records 61 extraction or syntax notifications. C1--C3 also receive deterministic completeness cues, while C0 has no cue-only counterpart. Accordingly, the experiment compares implemented context bundles; it does not isolate rationale text from accompanying cues or establish alert-level false-positive reduction.

\subsection{Execution, Matching, and Development Exposure}
Both investigator campaigns now contain all 1,548 scheduled cells, for 3,096 recorded v12 cells across the four arms. Completion of a scheduled cell is distinct from recognized completion of both official test phases. The final eight-arm comparison requires the original output and every candidate to have terminal-complete functional and security evaluations on the same 345 cases, leaving 42 admitted cases outside that comparison. DeepSeek additionally supports a 354-case four-arm analysis. An earlier interruption left 777 DeepSeek and 935 Gemini completed repair results, which are reused without regeneration. The remaining 771 and 613 cells use resumed execution with final public validation, exact-patch validation reuse, and bounded transport recovery; interrupted traces and their charged requests remain archived. The completed campaigns thus retain explicit execution-revision provenance rather than presenting the resumed work as a uniform rerun.

Development exposure is defined by a frozen task-level list. The original protected stratum contains 142 attempts across 48 tasks, and source-only exclusions leave 139 protected v12 admissions. Among the 345 shared terminal-complete cases, 110 are previously protected and 235 are development-exposed. The 354-case DeepSeek comparison contains 113 previously protected cases. These labels persist across generator attempts on the same task, preventing an inspected task from appearing independent merely because another generator produced it. The seven-version diagnostic progression instead uses the same ten repeatedly inspected cases, including one initially secure control. We report that progression as adaptive engineering evidence and retain the original cohorts for detailed historical gap and rescue audits.

\subsection{Outcome Definitions, Evidence Integrity, and Scope}
FuncPass and SecPass are the benchmark predicates under recognized framework-specific terminal completion, including its expected-failure allowances. We count original and final passes, conversions, regressions, and unresolved execution separately. The resulting rates describe post-processing of an admitted repair cohort rather than a new benchmark-wide generator pass@1, since investigation adds work after the original output. Reference security patches and hidden security tests are available only to retrospective evaluation, never to the investigator or its retry feedback. Reference-symbol overlap measures localization opportunity, and a supported hypothesis measures a protocol decision; neither substitutes for a passing security evaluation. Local environment recovery uses an independently evaluated original-output baseline and candidate under the same restored conditions, with exact-hash reuse recorded. The evidence pack binds source artifacts, cohort membership, normalized outcomes, and derived tables to hashes so every reported count can be recomputed locally.

The biological study uses qualified component checks and frozen feature requests to evaluate persistent repair memory in a different domain. Both conditions receive identical documentation-stripped code, while the memory condition also receives a repair note, enforced checks, and up to one feedback retry. We report first-proposal results and final joint feature-and-boundary success separately, because retaining an old repair does not complete a requested feature. The study is researcher-run on selected public repositories, with qualitative Barcelona practitioner review still pending. Statistical comparisons account for repeated attempts by resampling task clusters rather than treating every cell as independent; exploratory intervals use 5,000 percentile-bootstrap replicates with seed 12. Historical diagnostics, retained-patch reviews, and other continuation artifacts keep their original identities and selection records. Section~\ref{sec:threats} consolidates the remaining construct, causal, and generalization limits.

\section{Empirical Results: Coverage and Repair Outcomes}
\label{sec:results}
\subsection{RQ1: Evidence Available for Review}
Primary scanner locations overlap a reference file in 228/387 admitted attempts and a reference symbol in 52/387 (13.4\%). Including reported flow positions raises symbol overlap to 63/387 (16.3\%). The change-informed planner includes a reference symbol in 366/387 plans (94.6\%) and a complete reference-symbol body in 329. Table~\ref{tab:inventory} places these coverage measures beside the cohort inventory. Among the 291 publisher-SecFail attempts, primary symbol overlap is 41 and flow-inclusive overlap is 50, while the planner includes 281 reference targets. In the historical admission audit's 246 locally verified FuncPass/SecFail attempts, 37 have primary-symbol overlap and 237 have plan inclusion. Across these populations, patch-linked planning consistently makes relevant implementation context available beyond scanner positions.

The planner also explains why the snapshot configuration can investigate unseeded code. In the 335 attempts without a primary reference-symbol warning, C0 receives a patch-selected reference group in 317 and its complete body in 282. Functional requests independently mention the target in 307 of these attempts, giving the investigator another source of review context. Eight admitted attempts have only file-level reference mappings, which the coverage records preserve separately from named-symbol mappings. Scanner warnings also occur in publisher-SecPass outputs: 73/96 have a reference-file warning and eleven have a reference-symbol warning. The resulting review plan therefore combines independently useful warning provenance, changed-code context, and the feature request. This combination supplies the starting evidence on which the diagnosis and repair stages operate.

\finding{RQ1}{Change-informed planning includes reference-relevant symbols in 94.6\% of admitted review plans, compared with 13.4\% primary SAST symbol overlap. This is increased review coverage; detecting and repairing the missing security condition remains subsequent work.}

\subsection{RQ3: Context Bundles, Exposure, and Conversion Identity}
The strongest repeated ordering is that C2 is highest and C0 lowest among the four v12 SecPass counts for both investigators. C1 and C3 exchange positions between models, so their relative ordering varies by investigator. Table~\ref{tab:results} breaks the shared population down by all seven coding generators and by scanner and development exposure. The distinction matters because one task can contribute several generator attempts and several successful arms. On the common population, DeepSeek C2 makes eight conversions across six distinct tasks, while Gemini C2 makes seven across four tasks. These are improvements to specific generated implementations rather than fifteen independent vulnerability discoveries. The preserved conversion identities allow the per-generator counts to be traced back to those tasks. For C2 versus C0, the task-cluster 95\% intervals are [0.00, 2.96] percentage points for DeepSeek and [$-0.32$, 3.86] for Gemini, with six wins and one loss in each paired comparison.

The previously protected shared subset contains 110 attempts and 24 original security passes. DeepSeek C0--C3 reach 26/25/26/24, while Gemini reaches 25/27/27/25. C2 therefore ties C0 for DeepSeek and exceeds it by two cases for Gemini in this stratum. On the 235 development-exposed cases, the original 44 security passes become 45/48/50/50 for DeepSeek and 45/47/48/48 for Gemini. The full 354-case DeepSeek protected subset similarly starts at 24/113 and reaches 26/25/26/24. These strata show where the overall advantage occurs and how much of it extends beyond the development tasks. They also motivate examining the investigation stages, since supplying both channels does not consistently yield a better retained repair.

\finding{RQ3}{The rationale-enabled bundle ranks highest under both investigators, but combined temporal/rationale context does not improve on it. Protected-stratum gains over C0 are smaller: zero cases for DeepSeek and two for Gemini.}
