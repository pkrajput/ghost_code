\begin{abstract}
Agentic software development makes it possible to capture the process of code creation, moving beyond static comments and commit messages to preserve edits, tool interactions, and recorded ReAct-style reasoning behind implementation decisions. We present \tracer{} (Trace-based Runtime Analysis for Continuous Evolution and Release), a provenance-aware workflow that links task descriptions and recorded agent rationale to the evolution of code and its constituent symbols. We ask whether combining these reasoning traces with code evolution helps investigators understand implementation assumptions and better diagnose and fix security flaws. \tracer{} preserves diagnostic evidence, repair rationale, and associated executable boundary checks alongside each repair, providing persistent context for future updates, refactors, and feature additions. Across 3,096 repair runs on the SusVibes benchmark, \tracer{}'s symbol-level change tracking covers reference-vulnerable symbols in 94.6\% of attempts, compared with 13.4\% for stock SAST locations. The rationale-enabled configuration achieves the highest verified security pass rates among the evaluated configurations with both investigators, while an analysis of each step exposes where remaining candidates are lost during diagnosis and validation. Extending \tracer{} to real-world structural-biology repositories, we verify five component repairs and evaluate subsequent feature evolution under silent-fix conditions, where pairing persistent repair memory with a boundary gate and one feedback retry improves joint feature and security check success from~3/5~to~5/5.
\end{abstract}

\section{Introduction}
Autonomous coding agents can navigate repositories, edit source files, and execute test suites through interfaces such as SWE-agent~\cite{sweagent}, while agent-based repair systems extend this tool-driven workflow to debugging~\cite{repairagent}. For engineering teams adopting these systems, security remains a critical review obligation. Empirical studies of generated code and coding-assistant use document security weaknesses~\cite{asleep,perry,copilotweaknesses}. A patch can satisfy functional tests while leaving an unsafe input boundary, incomplete validation, or a violated API contract. SusVibes makes this gap explicit by evaluating functionality and security separately on repository-level tasks~\cite{susvibes,susvibesartifact}. Teams accepting working, agent-generated changes therefore need to uncover and repair omitted security conditions without breaking the requested functionality.

Existing software engineering defenses provide several starting points. Static application security testing (SAST) tools such as CodeQL~\cite{codeql} and Semgrep~\cite{semgrep} supply reproducible rules, source locations, and flow evidence. Industrial deployments and developer studies emphasize integrating actionable diagnostics into code review~\cite{johnson,googleanalysis,infer}. LLM-assisted taint and dataflow analysis~\cite{iris,llmdfa,repoaudit}, analyzer-guided repair~\cite{inferfix}, and program analysis guided proof of concept generation~\cite{pagent} further connect model judgments to source and execution evidence. These techniques help examine the implementation under review, but current-source findings alone do not explain why a coding agent omitted a guard or what it assumed about upstream inputs. When scanner locations also miss the relevant changed symbols, an investigator must first establish where to look and then reconstruct the missing security condition.

Agentic development offers the recorded process of code creation as an additional source of evidence. A trajectory can preserve intermediate edits, tool interactions, and interleaved ReAct-style explanations~\cite{react}, extending the evidence available from a final diff and commit message. Fine-grained AST differencing makes structural changes explicit~\cite{gumtree}, while recorded rationale supplies statements about input trust, callers, and library behavior. Together, these channels can expose a removed guard, an asymmetry between sibling functions, or a mismatch between an agent's stated assumption and its implementation. We treat explanations as hypotheses to check against current source, since generated rationale need not faithfully reveal internal reasoning~\cite{turpin,lanham}. The opportunity is to connect the history of a change to the present security contract that a repair must satisfy.

Repair is also a maintenance problem. Work on silent vulnerability fixes shows that security-relevant changes can lack an explicit security designation~\cite{colefunda}, and subsequent edits can undo an earlier repair, as explored in security-regression studies~\cite{undoingfix}. A later refactor or feature addition may preserve the requested behavior while losing a condition whose purpose is no longer apparent. The same provenance collected during investigation can carry that purpose forward. The diagnostic evidence, enforced invariant, and independently owned executable boundary check can remain linked to the repaired symbol. A maintenance workflow can then test subsequent changes against the saved contract and return concrete feedback when they violate it.

We present \tracer{} (Trace-based Runtime Analysis for Continuous Evolution and Release), a provenance-aware security investigation, repair, and maintenance workflow packaged as a lightweight, portable skill for integration with coding agents and continuous-integration pipelines. Given a bounded Git range or a compatible agent trajectory, \tracer{} performs symbol-level change tracking, keeps typed AST evolution separate from recorded rationale, grounds repair decisions in current-source assessment and conditional runtime checks, and emits persistent repair notes that can be coupled with executable boundary gates. Across 3,096 SusVibes repair runs spanning seven coding generators and two security investigators, DeepSeek-V3.2 and Gemini-3.8-Flash, \tracer{} includes reference-vulnerable symbols in 94.6\% of attempts, compared with 13.4\% primary SAST symbol overlap. The rationale-enabled configuration achieves the highest verified security pass counts with both investigators. Combining both history channels does not improve on it. A complementary study of structural-biology software~\cite{rfdiffusion,proteinmpnn,haddock3,dockq,vina,foldseek} verifies five component repairs and tests their subsequent feature evolution. Persistent memory with a one-retry boundary gate achieves joint feature-and-boundary success in 5/5 cases, compared with 3/5 for unguarded continuation.

The seven coding generators supply the original development trajectories, while the two security investigators apply the same review workflow to those saved outputs. This separates code creation from security investigation.

The paper makes three contributions.
\begin{itemize}
\item A provenance-aware architecture and portable skill. \tracer{} connects symbol-level change tracking, separate AST-evolution and rationale channels, guarded static/dynamic investigation, and persistent repair memory in a workflow that can accompany an agent-generated change.
\item A multi-investigator evaluation. The SusVibes study compares four context bundles across seven coding generators and two investigators, measuring review coverage, verified security outcomes, and functional preservation. The structural-biology study evaluates the maintenance stage under silent-fix feature evolution.
\item A four-step repair funnel and failure analysis. Tracing every repair attempt across four steps identifies where candidates are lost across diagnosis, turn scheduling, and semantic verification, providing concrete design lessons for agentic review systems.
\end{itemize}

\section{Background and Motivation}
\label{sec:motivation}
\subsection{Code Archaeology in Agent-Generated Pull Requests}
When an agent-generated pull request works, an industrial reviewer must still determine which implementation assumptions deserve scrutiny and which security conditions must survive later maintenance. CodeQL and Semgrep can report locations and flows in the final snapshot~\cite{codeql,semgrep}, but the reviewer must connect those findings to the submitted change, affected callers, and the intended contract. We call this reconstruction code archaeology. It recovers the context behind the current implementation from the evidence left available. The development trace adds context when the final diff omits an intermediate decision or correction.

In scientific software, checkpoint loading, structure parsing, archive extraction, and output paths expose boundaries that compatibility changes can weaken. Our study with Nostrum Biodiscovery examines these obligations. Preserving review evidence as reusable checks supports secure-development practices for testing and retaining vulnerability knowledge~\cite{ssdf}.

\subsection{Tracking Code Evolution Without AST Explosion}
Source lines shift, definitions are added or renamed, and refactoring changes function boundaries. Intermediate fragments may not parse. A temporal representation cannot assume stable node names or line positions. A line-based git diff records textual changes, but does not itself establish which function-level contract changed. CoLeFunDa's GumTree function-change descriptions~\cite{colefunda} inspire our compact summaries of symbol edits, which avoid carrying full ASTs across versions~\cite{gumtree,gumtree3}.

\subsection{Verifying Agent Intent and Recorded Reasoning}
Static analysis and AST differencing answer complementary questions about reported flows and structural changes, but neither alone supplies the requested behavior or every domain-specific assumption. Code can execute successfully while mishandling an input representation, trusting a caller without justification, or implementing only part of the task's contract. ReAct-style trajectories interleave explanations with actions~\cite{react}, allowing the task description, stated assumptions, and observed edits to be examined together. These recorded explanations are auditable claims, not guaranteed accounts of internal chain-of-thought~\cite{turpin,lanham}. A statement that an input is already validated, for example, creates a concrete obligation to inspect the relevant validator and its callers.

\section{TRACER Workflow and Architecture}
\label{sec:architecture}
\subsection{Symbol-Level Change Tracking and Static Analysis}
Figure~\ref{fig:architecture} shows an overview of the \tracer{} workflow. Rather than reviewing raw diff lines, \tracer{} indexes code at the symbol level using the standard-library \code{ast.parse} parser~\cite{pythonast}. For each snapshot, the index records functions, methods, and classes by their repository path, qualified name, line span, and structural hash. When a patch is submitted, \tracer{} maps modified lines to their enclosing symbols while excluding test and documentation files. It runs Semgrep~\cite{semgrep} and CodeQL~\cite{codeql} on the snapshot and attaches scanner warnings and flow evidence to the affected symbols. It also identifies guard conditions and possible callers in the same file to provide surrounding context. Scanner evidence retains its tool attribution and links to the changed function and surrounding code.

\subsection{Temporal AST Evolution via GumTree}
To track how modified symbols changed during development, \tracer{} parses before-and-after source pairs into typed Python ASTs and computes structural edit scripts using GumTree 3.0.0~\cite{gumtree,gumtree3}. It filters the operations to the target symbols and highlights added, modified, or removed guards and function calls. These summaries show how a symbol evolved without passing every historical file snapshot to the investigator. Related functions can reveal different validation choices within the same patch. Current code determines whether the suspected boundary is enforced. If a fragment fails to parse or a symbol cannot be linked across versions, \tracer{} marks the gap explicitly rather than assuming continuous tracking through arbitrary renames or refactors.

\subsection{Symbol-Linked Reasoning Traces}
Alongside the task description and code changes, \tracer{} extracts the coding agent's original ReAct-style explanations~\cite{react}. It excludes fenced code blocks so natural-language reasoning remains separate from source edits. It links excerpts through recorded file paths, symbol mentions, and matching edit fragments. Because an agent's stated rationale does not always match how its code behaves~\cite{turpin,lanham}, \tracer{} treats explanations as testable hypotheses. When an explanation states an assumption about inputs or callers, its quotation and verification plan are linked to the target symbol. The investigator can then check whether current source supports or contradicts the assumption. The quotation remains attached to its assessment so later reviewers can inspect the assumption and its supporting evidence.

\subsection{Decision Ledger, Repair Gate, and Post-Repair Maintenance}
The investigator records each security hypothesis, its target symbol, input boundary, and suspected flaw in a structured decision ledger saved as JSON. It checks static warnings against current source and inspects the historical evidence available in its configuration. When that evidence remains inconclusive, \tracer{} runs targeted Python checks following PAGENT's analysis-guided testing pattern~\cite{pagent}. These checks execute the target on normal and boundary inputs to observe whether the suspected flaw can be triggered. The repair gate requires a supported assessment, review of relevant downstream consumers, and public functional validation before accepting a candidate.

After a repair, \tracer{} saves a persistent note that binds its security invariant to the repaired symbol's hash and an independently owned executable boundary check. Future feature proposals are checked against ordinary tests, new feature tests, and the saved boundary check. The maintenance gate returns failure feedback for one bounded retry or retains the secure starting code.

The portable \code{tracer-security} skill\footnote{\url{https://github.com/pkrajput/TRACER_skill}} packages the symbol tracking and ledger workflow for host coding agents. Local helpers prepare scanner and history evidence. The host supplies editing and test interfaces, while CI can run saved checks on future commits without the benchmark harness.

\section{Experimental Setup}
\label{sec:design}
\subsection{Research Questions}
We structure the evaluation around five research questions that follow an agent-generated change from initial localization to subsequent maintenance. These are retrospective reporting questions for the completed experiments.

\noindent\textbf{RQ1 (Localization Coverage).} \emph{How effectively does symbol-level change tracking expose vulnerable symbols compared with stock SAST locations?}\par
Diagnosis requires bringing the relevant source into scope. We measure whether modified symbols and their relations expose reference-relevant code beyond scanner locations.

\smallskip
\noindent\textbf{RQ2 (End-to-End Verified Repair).} \emph{Does guarded investigation improve verified security outcomes without degrading functionality?}\par
Security interventions can break working features. We measure security conversions and functional regressions after source assessment, conditional runtime checks, and public functional validation.

\smallskip
\noindent\textbf{RQ3 (Provenance Channels).} \emph{How do temporal AST history, recorded rationale, and their combination affect verified repair?}\par
More context does not automatically produce better repairs. We compare the four configurations on identical attempts.

\smallskip
\noindent\textbf{RQ4 (Repair Funnel Bottlenecks).} \emph{Where are candidates lost between symbol localization and verified repair?}\par
High localization coverage does not guarantee a successful patch. A four-step repair funnel and qualitative failure analysis distinguish diagnostic, scheduling, semantic, and operational losses.

\smallskip
\noindent\textbf{RQ5 (Persistent Memory Under Silent-Fix Evolution).} \emph{Can repair memory and boundary gates preserve repaired properties while subsequent feature changes succeed?}\par
Later maintenance must satisfy both the new feature request and the earlier repair contract. We test this joint outcome in structural-biology software under silent-fix conditions.

\subsection{The SusVibes Benchmark and Study Dataset}
We evaluate the 186-task SusVibes v1.0 release, while the original paper reported benchmark statistics over 200 tasks~\cite{susvibes,susvibesartifact}. The benchmark evaluates agent-generated features in full repositories using separate functional and security tests. In the original sample, repositories averaged 162K lines across 867 files, and reference implementations averaged 172.1 edited lines across 1.8 files. The original tasks spanned 108 projects and 77 CWE categories. Their security fixes averaged 29.5 lines across 1.6 files. Tasks had an average of 68.8 functional tests and 3.7 security tests. Agents therefore work with existing interfaces and callers, not isolated functions.

Table~\ref{tab:inventory} lists outputs from seven coding generators across 186 Python tasks, yielding 1,302 archived patches. Of these, 472 have publisher-reported functional success. Source screening and local environment reproduction admit 387 patches across 118 tasks. Original evaluations reach recognized completion for 354 patches. Among them, 350 pass functional tests and 69 pass security tests. Admission therefore reflects the publisher's functional label, while the table reports our locally verified outcomes.

\subsection{Evaluated Configurations and Investigator Models}
We use DeepSeek-V3.2 through OpenRouter's SiliconFlow FP8 endpoint and Gemini-3.8-Flash through the native Gemini API as the two security investigators. Both use temperature zero, a 22-turn cap, and a 100,000-byte message budget. Gemini uses LOW thinking. Each configuration receives the functional request, modified symbols, scanner findings, and the same repair protocol.
\begin{itemize}
\item \textbf{C0 (Snapshot + SAST).} Current source of the modified symbols and static warnings, without historical AST edits or recorded reasoning.
\item \textbf{C1 (C0 + Temporal AST).} Adds structural edits showing how those symbols evolved.
\item \textbf{C2 (C0 + Recorded Rationale).} Adds the coding agent's original development explanations.
\item \textbf{C3 (C0 + Both).} Combines temporal AST edits and recorded explanations.
\end{itemize}
The seven models in Table~\ref{tab:inventory} are coding generators that wrote the original patches, whereas the two fixed investigators review and repair every generator's outputs. C1, C2, and C3 also receive audit cues absent from C0, so the comparison evaluates complete context configurations rather than isolating each provenance channel alone.

All configurations use Semgrep CE 1.101.0 with Python rules at commit \code{495df89c} and CodeQL 2.20.0 with Python queries 1.3.4 and the security-extended suite. The Semgrep set includes correctness and maintainability rules as well as security rules. Investigation inputs scope warnings to changed files and at most twelve symbol groups. Coverage audits use the full scanner output. SAST-seeded patches receive at least one scoped warning, while unseeded patches receive none. The benchmark hides prior Git history to prevent recovery of historical fixes, so the evaluated history comes from the coding agent's recorded trajectory after the reference commit.

\subsection{Evaluation Protocol}
We use SusVibes's official functional and security tests inside isolated containers. FuncPass and SecPass require recognized terminal test summaries, including the benchmark's expected-failure allowances. Hidden security tests and reference patches are used only for retrospective evaluation and are never supplied as investigation or retry feedback. Investigators receive public functional feedback.

Each admitted patch is reviewed in four configurations by two investigators, producing 3,096 repair runs. Table~\ref{tab:results} compares 345 patches with completed original and candidate evaluations across all eight configurations. DeepSeek also supports a comparison over 354 patches. An investigator error can leave a retained patch or a no-op that is later evaluated. Recovery checks originals and candidates in the same restored environment and reuses results only for identical patches. We report conditional repair outcomes, rather than new benchmark-wide generator pass@1 scores. Task-cluster intervals use 5,000 bootstrap replicates with seed 12 to account for repeated generator attempts~\cite{bootstrap}.

A security conversion requires an originally failing security outcome to become a verified pass after repair. Preserving an original pass is recorded separately. An incomplete evaluation remains unresolved and is not counted as a failed security assertion. This distinction matters when a repair process is interrupted but its saved candidate can still be evaluated locally.

\section{Benchmark Repair Results (RQ1-RQ3)}
\label{sec:results}
\subsection{RQ1. Symbol Localization Coverage}
\noindent\textbf{RQ1.} \emph{How effectively does symbol-level change tracking expose vulnerable symbols compared with stock SAST locations?}\par\smallskip
Across 387 admitted patches, CodeQL and Semgrep warnings overlap a reference security file in 228 cases (58.9\%). Primary warning locations overlap a reference symbol in 52 cases (13.4\%). Including flow endpoints raises this to 63 cases (16.3\%). These are measures of reference-symbol review coverage, not vulnerability detection recall.

Tracking modified symbols and their relations includes a reference symbol in 366 review scopes (94.6\%). It supplies the complete body in 329 cases. Among the 335 patches without a primary warning on the reference symbol, change tracking supplies its full body in 282 cases. The task request also names the reference target in 307 of those patches. These inputs bring relevant implementation context into scope before diagnosis begins.

The file and symbol measures answer different review questions. A warning elsewhere in a large file does not necessarily direct attention to the relevant function. Providing the function body gives the investigator a concrete implementation to inspect. The next step is to connect that implementation to an input, caller, or output contract that can be checked. The task describes the intended behavior, while the changed symbol identifies its implementation. Reading both helps frame a security question without assuming that a reference-symbol match establishes the missing condition.

\rqfinding{RQ1 Finding}{\tracer{} includes reference symbols in 94.6\% of review scopes, compared with 13.4\% for primary SAST locations.}

\subsection{RQ3. Impact of Provenance Channels}
\noindent\textbf{RQ3.} \emph{How do temporal AST history, recorded rationale, and their combination affect verified repair?}\par\smallskip
Recorded rationale achieves the highest aggregate SecPass count with both investigators. Its explanations give the investigator claims about input validation, caller trust, or library behavior to check against the current implementation. DeepSeek C2 makes eight conversions across six distinct tasks, while Gemini C2 makes seven across four tasks. These count repaired generator outputs rather than independent vulnerability discoveries.

Different generators can implement the same feature with different checks and assumptions. The generator breakdown shows whether the aggregate advantage is concentrated in one source of code, while paired configurations review the same archived patch.

Combining both channels yields fewer verified repairs than rationale alone. Context dilution is a possible explanation. DeepSeek falls from 76 security passes in C2 to 74 in C3, and Gemini falls from 75 to 73. Table~\ref{tab:results} shows that individual generator rankings vary. For C2 versus C0, each investigator has six wins and one loss. The task-cluster 95\% intervals are 0.00 to 2.96 percentage points for DeepSeek and $-0.32$ to 3.86 for Gemini.

Table~\ref{tab:results} separates 235 development-exposed patches from 110 previously protected patches, on which C2 adds zero security passes over C0 for DeepSeek and two for Gemini.

\rqfinding{RQ3 Finding}{Recorded rationale ranks highest overall with both investigators, while combining both history channels yields fewer verified security passes.}
