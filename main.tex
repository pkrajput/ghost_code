\begin{abstract}
Agentic software development makes it possible to capture the process of code creation, moving beyond static comments and commit messages to preserve edits, tool interactions, and recorded ReAct-style reasoning behind implementation decisions. We present \tracer{} (Trace-based Runtime Analysis for Continuous Evolution and Release), a provenance-aware workflow that links task descriptions and recorded agent rationale to the evolution of code and its constituent symbols. We ask whether combining these reasoning traces with code evolution helps investigators understand implementation assumptions and better diagnose and fix security flaws. \tracer{} preserves diagnostic evidence, repair rationale, and associated executable boundary checks alongside each repair, providing persistent context for future updates, refactors, and feature additions. Across 3,096 repair runs on the SusVibes benchmark, \tracer{}'s change-informed planning covers reference-vulnerable symbols in 94.6\% of attempts, compared with 13.4\% for stock SAST locations. The rationale-enabled configuration achieves the highest verified security pass rates among the evaluated configurations with both investigators, while a stage-level analysis exposes where remaining candidates are lost during diagnosis and validation. Extending \tracer{} to real-world structural-biology repositories, we verify five component repairs and evaluate subsequent feature evolution under silent-fix conditions, where pairing persistent repair memory with a boundary gate and one feedback retry improves joint feature-and-security-check success from 3/5 to 5/5.
\end{abstract}

\section{Introduction}
Autonomous coding agents can navigate repositories, edit source files, and execute test suites through interfaces such as SWE-agent~\cite{sweagent}, while agent-based repair systems extend this tool-driven workflow to debugging~\cite{repairagent}. For engineering teams adopting these systems, security remains a critical review obligation. Empirical studies of generated code and coding-assistant use document security weaknesses~\cite{asleep,perry,copilotweaknesses}: a patch can satisfy functional tests while leaving an unsafe input boundary, incomplete validation, or a violated API contract. SusVibes makes this gap explicit by evaluating functionality and security separately on repository-level tasks~\cite{susvibes,susvibesartifact}. Teams accepting working, agent-generated changes therefore need to uncover and repair omitted security conditions without breaking the requested functionality.

Existing software engineering defenses provide several starting points. Static application security testing (SAST) tools such as CodeQL~\cite{codeql} and Semgrep~\cite{semgrep} supply reproducible rules, source locations, and flow evidence. Industrial deployments and developer studies emphasize integrating actionable diagnostics into code review~\cite{johnson,googleanalysis,infer}. LLM-assisted taint and dataflow analysis~\cite{iris,llmdfa,repoaudit}, analyzer-guided repair~\cite{inferfix}, and program-analysis-guided proof-of-concept generation~\cite{pagent} further connect model judgments to source and execution evidence. These techniques help examine the implementation under review, but current-source findings alone do not explain why a coding agent omitted a guard or what it assumed about upstream inputs. When scanner locations also miss the relevant changed symbols, an investigator must first establish where to look and then reconstruct the missing security condition.

Agentic development offers an additional source of evidence: the recorded process of code creation. A trajectory can preserve intermediate edits, tool interactions, and interleaved ReAct-style explanations~\cite{react}, extending the evidence available from a final diff and commit message. Fine-grained AST differencing makes structural changes explicit~\cite{gumtree}, while recorded rationale supplies statements about input trust, callers, and library behavior. Together, these channels can expose a removed guard, an asymmetry between sibling functions, or a mismatch between an agent's stated assumption and its implementation. We treat explanations as hypotheses to check against current source, since generated rationale need not faithfully reveal internal reasoning~\cite{turpin,lanham}. The opportunity is to connect the history of a change to the present security contract that a repair must satisfy.

Repair is also a maintenance problem. Work on silent vulnerability fixes shows that security-relevant changes can lack an explicit security designation~\cite{colefunda}, and subsequent edits can undo an earlier repair, as explored in security-regression studies~\cite{undoingfix}. A later refactor or feature addition may preserve the requested behavior while losing a condition whose purpose is no longer apparent. The same provenance collected during investigation can carry that purpose forward: the diagnostic evidence, enforced invariant, and independently owned executable boundary check can remain linked to the repaired symbol. A maintenance workflow can then test subsequent changes against the saved contract and return concrete feedback when they violate it.

We present \tracer{} (\emph{Trace-based Runtime Analysis for Continuous Evolution and Release}), a provenance-aware security investigation, repair, and maintenance workflow packaged as a lightweight, portable skill for integration with coding agents and continuous-integration pipelines. Given a bounded Git range or a compatible agent trajectory, \tracer{} performs change-informed symbol planning, keeps typed AST evolution separate from recorded rationale, grounds repair decisions in current-source assessment and conditional runtime checks, and emits persistent repair notes that can be coupled with executable boundary gates. Across 3,096 SusVibes repair runs spanning seven coding generators and two security investigators, its planner includes reference-vulnerable symbols in 94.6\% of attempts, compared with 13.4\% primary SAST symbol overlap. The rationale-enabled configuration achieves the highest verified security pass counts with both investigators; combining both history channels does not improve on it. A complementary study of structural-biology software~\cite{rfdiffusion,proteinmpnn,haddock3,dockq,vina,foldseek} verifies five component repairs and tests their subsequent feature evolution. Persistent memory with a one-retry boundary gate achieves joint feature-and-boundary success in 5/5 cases, compared with 3/5 for unguarded continuation.

The paper makes three contributions:
\begin{itemize}
    \item \textbf{A provenance-aware architecture and portable skill.} \tracer{} connects change-informed planning, separate AST-evolution and rationale channels, guarded static/dynamic investigation, and persistent repair memory in a workflow that can accompany an agent-generated change through later maintenance.
    \item \textbf{A multi-investigator evaluation.} The SusVibes study compares four context bundles across seven coding generators and two investigators, measuring review coverage, verified security outcomes, and functional preservation. The structural-biology study evaluates the maintenance stage under silent-fix feature evolution.
    \item \textbf{A stage-level funnel and failure taxonomy.} A seven-version engineering progression and a full-cohort investigation funnel identify losses during diagnosis, validation scheduling, patch retention, and semantic repair, providing concrete design lessons for agentic review systems.
\end{itemize}

\section{Background and Motivation}
\label{sec:motivation}
\subsection{Industry Relevance and Code Archaeology}
A working agent-generated pull request leaves an industrial reviewer with two questions: which implementation assumptions deserve scrutiny, and which security conditions must survive later maintenance? CodeQL and Semgrep can report locations and flows in the final snapshot~\cite{codeql,semgrep}, but the reviewer must connect those findings to the submitted change, affected callers, and the intended contract. We call this reconstruction \emph{code archaeology}: recovering the context behind the current implementation from the evidence left available. Industrial static-analysis studies emphasize actionable diagnostics, developer trust, and integration into existing review workflows~\cite{johnson,googleanalysis,infer}. Preserving the development trace can supply context for that review, especially when the final diff omits an intermediate decision or correction.

For scientific-software teams such as Nostrum Biodiscovery, checkpoint loading, structure parsing, archive extraction, and output-path handling are concrete interfaces where compatibility requests can invalidate earlier assumptions. A useful workflow must investigate these boundaries while preserving the requested scientific functionality, then retain the repair's purpose for the next change. Connecting review evidence to reusable checks fits secure-development practices for code review, testing, and retaining vulnerability knowledge~\cite{ssdf}. Our domain study examines these component-level obligations; production effectiveness remains to be evaluated.

\subsection{Tracking Structural Evolution Within a Bounded Context}
Making history available is not equivalent to making it usable. Source lines shift, definitions are added or renamed, and refactoring changes how code is divided among functions and classes; intermediate fragments may not parse. A temporal representation therefore cannot assume that node names or line positions remain stable across versions. A line-based \code{git diff} records textual changes, but does not itself establish which function-level contract changed. Retaining every full AST and cross-version relation also expands the context with repeated or irrelevant structure. Fine-grained AST matching through GumTree~\cite{gumtree,gumtree3}, together with function-change representations such as CoLeFunDa's~\cite{colefunda}, motivates a more focused representation: map observed changes to symbols, summarize their structural edits, and preserve explicit gaps where continuity cannot be established.

\subsection{Task Intent and Recorded Reasoning}
Static analysis and AST differencing answer complementary questions about reported flows and structural changes, but neither alone supplies the requested behavior or every domain-specific assumption. Code can execute successfully while mishandling an input representation, trusting a caller without justification, or implementing only part of the task's contract. ReAct-style trajectories interleave explanations with actions~\cite{react}, allowing the task description, stated assumptions, and observed edits to be examined together. These recorded explanations are auditable claims, not guaranteed accounts of internal chain-of-thought~\cite{turpin,lanham}. A statement that an input is already validated, for example, creates a concrete obligation to inspect the relevant validator and its callers.

Our motivating cases come from repository tasks in SusVibes~\cite{susvibes,susvibesartifact}. In Python-RSA,\footnote{\url{https://github.com/sybrenstuvel/python-rsa}} comparing \code{decrypt} and \code{verify} exposes an asymmetric encoded-input-length guard; LangChain\footnote{\url{https://github.com/langchain-ai/langchain}} similarly illustrates an incomplete origin condition that checks network location but omits scheme equality. Wagtail CMS\footnote{\url{https://github.com/wagtail/wagtail}} shows the danger of repairing an intermediate label without inspecting downstream rendering: an early candidate introduces double-escaping. In Django,\footnote{\url{https://github.com/django/django}} recorded rationale favors character-reference conversion in \code{strip_tags}, while its tested contract requires preserving relevant text representations; a partial handler repair still fails. These cases motivate both discovering missing invariants and checking a proposed repair at the correct boundary.

\subsection{Symbol-Level Tracking and Snapshot SAST (C0)}
\tracer{} uses Python's standard-library \code{ast} parser, specifically \code{ast.parse}~\cite{pythonast}, with its own symbol visitor in \code{planner.py}. Functions, asynchronous functions, methods, and classes are identified by repository path, qualified name, and definition span; the history adapter also records structural hashes. Rather than using diff lines as the review unit, the planner maps submitted patch hunks and deletion anchors to their enclosing current symbols, excludes test and documentation paths, and records module-level or unavailable mappings when needed. It links guards, candidate in-file callers, and related changed symbols, while attributing Semgrep and CodeQL locations and flow evidence to their originating scanners~\cite{semgrep,codeql}. Local call-name matches are syntactic review hints, not resolved dataflow. This channel defines C0: a change-informed snapshot review that scopes investigation beyond scanner locations, but still requires archaeology to explain how and why the current symbol was written.

\subsection{Temporal AST Evolution via GumTree (C1)}
C1 adds the observed structural evolution of selected symbols. \tracer{} parses available before/after source pairs into typed Python ASTs and computes edit scripts with GumTree 3.0.0~\cite{gumtree,gumtree3}. It filters operations to the target symbols, retains guards and calls inside parent-subtree additions, normalizes recoverable fragment indentation, and bounds operations, symbol summaries, and delivered characters. The resulting hints describe changes without passing every historical snapshot to the investigator. Cutoff-bounded Git ancestry and recorded agent edits retain separate provenance. Path/name associations and unique fragment anchors link evidence to current symbols; continuity gaps, parse failures, and truncation remain explicit rather than implying complete identity tracking through arbitrary renames or refactors.

\subsection{Symbol-Linked Reasoning Traces (C2 and C3)}
The task description is shared context for every configuration. C2 additionally retrieves original ReAct-style development prose~\cite{react}, excluding fenced code so explanations remain separate from source changes. The extractor links excerpts through recorded action paths, symbol mentions, and uniquely matched edit fragments, retaining event IDs, offsets, and source hashes; a file association remains distinguishable from a current-symbol anchor. When an excerpt informs a hypothesis, its quotation, testable assumption, and verification plan are stored with that hypothesis's target symbol in the decision ledger. The investigator records whether current evidence supports, contradicts, or leaves the assumption unresolved, since rationale is not authoritative evidence of behavior~\cite{turpin,lanham}. C3 combines these rationale links with C1's temporal AST evidence and divergence cues; rationale retrieval remains available even when an old AST cannot be reconstructed.

\subsection{Decision Ledger, Repair Gate, and Portable Skill}
The investigator records a hypothesis's target symbol, input boundary, and alleged violated property in a structured decision ledger, serialized in \code{edit_note.json}. It grounds assessments in quotations from the current source and, when evidence remains inconclusive, bounded Python checks following PAGENT's analysis-guided testing pattern~\cite{pagent}. Checks record the source version, target reachability, ordinary-input behavior, and boundary observations. The repair gate requires a supported defect, review of relevant downstream consumers, and validation of the candidate against public functional tests. Assessments and checks must apply to the current candidate; the note preserves their evidence links alongside patch, source, and trajectory identities.

For Stage~4 maintenance, a qualified repair note additionally binds the security invariant to the exact repaired-symbol hash and an independently owned executable boundary check. Subsequent feature proposals must satisfy ordinary, feature, and saved boundary checks. The continuation gate returns failure feedback for a bounded retry or retains the qualified starting code, recording acceptance and fallback separately.

The portable \code{tracer-security} skill packages this symbol-tracking and ledger workflow for a host coding agent. Local helpers consume a bounded Git history or compatible recorded trajectory and produce review evidence using the available scanner and history adapters. The host supplies its editing and test interface, while a CI pipeline can run the saved checks on later changes. This separation supports adoption without depending on the SusVibes runner or its hidden evaluation tests.

\section{Experimental Design and Reproducibility}
\label{sec:design}
\subsection{Research Questions}
We structure the evaluation around five research questions that follow an agent-generated change from initial localization to subsequent maintenance. These are retrospective reporting questions for the completed experiments.

\noindent\textbf{RQ1 (Localization Coverage):} \emph{How effectively does change-informed planning expose vulnerable symbols compared with stock SAST locations?}\par
\noindent\emph{Rationale:} Diagnosis requires bringing the relevant source into scope. We measure whether patch-selected symbols and their relations expose reference-relevant code beyond the locations reported by the scanners.

\smallskip
\noindent\textbf{RQ2 (End-to-End Verified Repair):} \emph{Does guarded investigation improve verified security outcomes without degrading functionality?}\par
\noindent\emph{Rationale:} Security interventions can break working features. We measure security conversions and functional regressions after current-source assessment, conditional runtime checks, and public functional validation.

\smallskip
\noindent\textbf{RQ3 (Provenance Channels):} \emph{How do temporal AST history, recorded rationale, and their combination affect verified repair?}\par
\noindent\emph{Rationale:} More context does not automatically produce better repairs. Comparing the four implemented bundles on identical attempts measures their relative contribution, with accompanying audit cues treated as part of each bundle.

\smallskip
\noindent\textbf{RQ4 (Stage-Level Bottlenecks):} \emph{Where are candidates lost between symbol localization and verified repair?}\par
\noindent\emph{Rationale:} Review coverage does not guarantee a successful patch. A seven-version development study and a four-stage investigation funnel distinguish diagnostic, validation, semantic, and operational losses.

\smallskip
\noindent\textbf{RQ5 (Persistent Memory Under Silent-Fix Evolution):} \emph{Can repair memory and boundary gates preserve repaired properties while subsequent feature changes succeed?}\par
\noindent\emph{Rationale:} Later maintenance must satisfy both the new feature request and the earlier repair contract. We test whether saved repair notes and executable checks support that joint outcome in structural-biology software under silent-fix conditions.

Seven generators each contribute 186 tasks, yielding 1,302 archived attempts. \subsection{Investigated Configurations}
The investigators are \path{deepseek/deepseek-v3.2} through \path{siliconflow/fp8} and \path{gemini-3.8-flash} through the native Gemini endpoint. Both configure temperature zero, with LOW thinking for Gemini. Each v12 cell permits 22 turns under a shared 100,000-byte message setting. All configurations receive the functional request, patch-selected current source, scanner context, and the same guarded action protocol:
\begin{itemize}
    \item \textbf{C0: Snapshot + SAST.} A change-informed current-source review with scanner findings, without temporal AST history or recorded development rationale.
    \item \textbf{C1: + Temporal AST.} C0 with the observed sequence of structural code changes.
    \item \textbf{C2: + Recorded Rationale.} C0 with the agent's recorded development explanations.
    \item \textbf{C3: Combined Temporal + Rationale.} C0 with both channels and linked divergence evidence.
\end{itemize}
C0 is a change-informed snapshot comparator related to analyzer-guided repair~\cite{inferfix}; it already receives targets selected from the agent patch. C1--C3 also receive deterministic completeness cues, while C0 has no cue-only counterpart. The comparison therefore evaluates implemented context bundles, rather than isolating rationale text from accompanying cues. The benchmark withholds upstream Git ancestry to avoid revealing masked implementations, so measured temporal evidence comes from the archived post-reference agent trajectory.

All configurations share pinned scanner manifests: Semgrep CE 1.101.0 with Python rules at commit \code{495df89c}, and CodeQL 2.20.0 with Python queries 1.3.4 and the security-extended suite. The Semgrep directory includes correctness and maintainability rules alongside security checks. Scans use an oracle-free source export, after which prompt planning scopes findings to changed files and at most twelve groups. The overlap audit retains the full scanner output rather than only the delivered warning subset; the comparison does not establish alert-level false-positive reduction.

\subsection{Reproducibility and Execution Integrity}
FuncPass and SecPass are the benchmark predicates under recognized framework-specific terminal completion, including expected-failure allowances. We count original and final passes, conversions, regressions, and unresolved execution separately. These are post-processing outcomes on an admitted repair cohort, not new benchmark-wide generator pass@1 estimates. Reference security patches and hidden security tests are available only to retrospective evaluation, never to investigators or their retry feedback. Reference-symbol overlap measures review opportunity, and a supported assessment records a protocol decision; neither substitutes for a passing security evaluation. Local environment recovery independently evaluates the original output and candidate under the same restored conditions, with exact-hash reuse recorded. Source artifacts, cohort membership, outcomes, and derived tables are bound to hashes for local recomputation.

Each investigator campaign contains all 1,548 scheduled cells, giving 3,096 recorded v12 cells. The shared comparison requires recognized functional and security completion for the original output and all eight candidates on the same 345 attempts; 42 admissions remain outside this comparison. DeepSeek additionally supports a 354-case four-arm comparison, while historical v6 results use 302 fully matched attempts. Development exposure follows a frozen task-level list: the original protected stratum has 142 attempts across 48 tasks, with 139 admissions remaining after source-only exclusions. The shared cohort contains 110 previously protected and 235 development-exposed attempts; the DeepSeek-only comparison contains 113 previously protected attempts. Labels persist across generators for a given task. The separate seven-version progression repeatedly inspects the same ten cases, including one initially secure control, and is reported as adaptive engineering evidence.

For RQ5, qualified component checks and frozen feature requests evaluate persistent repair memory. Both conditions receive identical documentation-stripped source; Memory+Gate additionally receives a repair note, enforced checks, and up to one feedback retry. First-proposal outcomes, final joint feature-and-boundary success, and fallback preservation are reported separately because retaining old code does not implement the requested feature. Statistical comparisons of benchmark outcomes account for repeated generator attempts through task-cluster resampling; exploratory intervals use 5,000 percentile-bootstrap replicates with seed 12~\cite{bootstrap}. Historical diagnostics, retained-patch reviews, and continuation artifacts keep their original identities and selection records; Section~\ref{sec:threats} consolidates the remaining validity limits.

Execution provenance records the preparation and recovery details behind these populations. Of the publisher-FuncPass outputs, 59 do not reproduce functional success during preparation, 20 lack source, and two have incomplete scans; four further exclusions comprise three unparsable primary Python files and one patch without a current production review target. Scanner diagnostics include 37 notifications across 23 Semgrep runs, including 25 timeouts, and 61 CodeQL extraction or syntax notifications. A corrected evaluation parser requires terminal summaries rather than inferring completion from absent failure counts. An interruption leaves 777 DeepSeek and 935 Gemini repair results, reused without regeneration; the remaining 771 and 613 cells run under resumed execution with final public validation, exact-patch validation reuse, and bounded transport recovery. Interrupted traces, charged requests, and execution-revision identities remain archived, so the completed study is not presented as a uniform rerun.

\section{Empirical Results: Coverage and Repair Outcomes}
\label{sec:results}
\subsection{RQ1: Evidence Available for Review}
Primary scanner locations overlap a reference file in 228/387 admitted attempts and a reference symbol in 52/387 (13.4\%). Including reported flow positions raises symbol overlap to 63/387 (16.3\%). The change-informed planner includes a reference symbol in 366/387 plans (94.6\%) and a complete reference-symbol body in 329. Table~\ref{tab:inventory} places these coverage measures beside the cohort inventory. Among the 291 publisher-SecFail attempts, primary symbol overlap is 41 and flow-inclusive overlap is 50, while the planner includes 281 reference targets. In the historical admission audit's 246 locally verified FuncPass/SecFail attempts, 37 have primary-symbol overlap and 237 have plan inclusion. Across these populations, patch-linked planning consistently makes relevant implementation context available beyond scanner positions.

The planner also explains why the snapshot configuration can investigate unseeded code. In the 335 attempts without a primary reference-symbol warning, C0 receives a patch-selected reference group in 317 and its complete body in 282. Functional requests independently mention the target in 307 of these attempts, giving the investigator another source of review context. Eight admitted attempts have only file-level reference mappings, which the coverage records preserve separately from named-symbol mappings. Scanner warnings also occur in publisher-SecPass outputs: 73/96 have a reference-file warning and eleven have a reference-symbol warning. The resulting review plan therefore combines independently useful warning provenance, changed-code context, and the feature request. This combination supplies the starting evidence on which the diagnosis and repair stages operate.

\rqfinding{RQ1 Finding}{Change-informed planning includes reference-relevant symbols in 94.6\% of admitted review plans, compared with 13.4\% primary SAST symbol overlap. This is increased review coverage; detecting and repairing the missing security condition remains subsequent work.}

\subsection{RQ3: Context Bundles, Exposure, and Conversion Identity}
The strongest repeated ordering is that C2 is highest and C0 lowest among the four v12 SecPass counts for both investigators. C1 and C3 exchange positions between models, so their relative ordering varies by investigator. Table~\ref{tab:results} breaks the shared population down by all seven coding generators and by scanner and development exposure. The distinction matters because one task can contribute several generator attempts and several successful arms. On the common population, DeepSeek C2 makes eight conversions across six distinct tasks, while Gemini C2 makes seven across four tasks. These are improvements to specific generated implementations rather than fifteen independent vulnerability discoveries. The preserved conversion identities allow the per-generator counts to be traced back to those tasks. For C2 versus C0, the task-cluster 95\% intervals are [0.00, 2.96] percentage points for DeepSeek and [$-0.32$, 3.86] for Gemini, with six wins and one loss in each paired comparison.

The previously protected shared subset contains 110 attempts and 24 original security passes. DeepSeek C0--C3 reach 26/25/26/24, while Gemini reaches 25/27/27/25. C2 therefore ties C0 for DeepSeek and exceeds it by two cases for Gemini in this stratum. On the 235 development-exposed cases, the original 44 security passes become 45/48/50/50 for DeepSeek and 45/47/48/48 for Gemini. The full 354-case DeepSeek protected subset similarly starts at 24/113 and reaches 26/25/26/24. These strata show where the overall advantage occurs and how much of it extends beyond the development tasks. They also motivate examining the investigation stages, since supplying both channels does not consistently yield a better retained repair.
