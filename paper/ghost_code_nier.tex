\title{Development Histories as Software Evidence}
\author{}
\begin{document}
\maketitle

\begin{abstract}
Software development produces explanations, actions, and intermediate code whose relationships can be lost after a task ends. Coding-agent sessions offer an opportunity to preserve this process as reusable software evidence. We introduce \tracer{} (Trace-based Runtime Analysis for Code Evolution Review), an architecture that links recorded reasoning and actions to file and symbol changes, preserves revisions, and derives a decision ledger. Such histories bring natural-language context together with code evolution for human inspection, subsequent agents, and software analysis. We investigate one use by combining static analysis of mini-SWE-agent trajectories on SWE-bench with a qualitative review of recorded agent explanations. We trace the creation and use of retained helper scripts before examining their embedded source code. The analysis recovers 62 human-reviewed reference helpers whose removal preserved passing task outcomes. Among the embedded implementations linked to product code, some match its final version and others have been superseded. An initial author review of the recorded explanations connects stated repair decisions to the observed code revisions. This case study shows how linking language with code evolution clarifies artifacts left by an agent and motivates evaluation of history-informed review and task continuation.
\end{abstract}
\begin{IEEEkeywords}
development history, coding agents, software provenance, static analysis
\end{IEEEkeywords}

\section{Introduction}
Understanding a software change requires context. Source versions preserve edits, while explanations and observations may be dispersed across discussions, logs, and temporary workspaces. Intermediate attempts can disappear before a commit. Later reviewers and agents must reconstruct their relationships. Preserving those relationships during development would make the process available for inspection and reuse.

Coding agents offer a practical opportunity to capture this context at each development action. Systems such as SWE-agent and OpenHands edit and execute code through recorded interfaces~\cite{sweagent,openhands,codeact}. Natural-language records describe expressed rationale, including exposed chain of thought (CoT) where available. Commands, observations, and code versions document the associated activity. Linking these records lets an analyst inspect an explanation alongside changes recorded in the same step. We propose treating linked development histories as reusable software evidence. \tracer{}: \emph{Trace-based Runtime Analysis for Code Evolution Review}, connects steps to file and symbol changes through Git diffs, preserves revisions, and derives a decision ledger. Its adapter contract separates recording from particular agents and analyses. The aim is to retain context before its recovery becomes an archaeology task. Available reasoning is part of this evidence, without assuming access to hidden thought or treating recorded explanations as faithful intent.

Linked histories could help developers review repair attempts, subsequent agents recover prior observations, and program analyses explain artifacts left in a workspace. We investigate helper scripts that survive an agent session. AST analysis and recorded actions establish their source-writing role, while saved deletion trials determine whether removal preserves the passing task-oracle outcome. We call these task-redundant helpers \emph{ghost scripts}. The label concerns the endpoint, even when a helper was useful during development. We then examine what these scripts retain. Some embed the final product implementation as string data, others preserve superseded attempts, and some have no complete embedded definition that can be linked to the product. Recorded language can explain why an agent created or revised a helper while leaving its reason for retention unstated. Our SWE-bench study~\cite{swebench} combines this static evidence with human review of the reference helpers and selected agent explanations.

We contribute \tracer{}, an architecture for preserving linked development histories, and an AST analysis that uses those histories to identify construction helpers and follow their embedded implementations. We demonstrate the decision ledger on preserved source histories and study retained helpers through retrospective analysis and human verification. These contributions make the origin of retained code, its revisions, and the agent's expressed reasons available for inspection.

\section{TRACER Architecture}
\label{sec:tracer}

\begin{figure*}[t]
\centering
\includegraphics[width=\textwidth]{figures/tracer_ghost_script_overview.pdf}
\caption{\tracer{} links recorded explanations, actions, and code revisions into a reusable development history (top). The ghost-script application follows helper trajectories and embedded code, joins saved deletion outcomes, and checks five selected language interpretations with an author (bottom).}
\label{fig:overview}
\end{figure*}
\tracer{} preserves actions, code revisions, and recorded explanations as linked development histories (Figure~\ref{fig:overview}). Its architecture separates agent adapters, a recording core, and analysis modules. Each step associates the prompt and available reasoning with the action's before/after versions. The structural index supplied by \code{codebase-memory-mcp}~\cite{codebasememory} provides symbol names, source spans, and relationships. Git diffs locate edits, and AST information maps them to functions and classes, with file-level links when a symbol cannot be resolved. Analysts can follow a symbol's revisions alongside the explanations recorded at each step. Narration, tool-call thoughts, exposed CoT, and provider summaries retain their source fields. Without a compatible index, the recorder uses file-level links.

Git snapshots preserve intermediate attempts. A decision ledger derives survival, revision, and abandonment labels from Git line differences and symbol presence without an LLM. These labels guide review of code evolution. Branch histories, reasoning search, and versioned file/symbol queries expose earlier attempts through a review timeline. The tool supports OpenHands and human-edit interfaces alongside the mini-SWE-agent connector used here. Existing agents already persist trajectories and conversation state~\cite{mini,ohpersistence}. \tracer{} adds explicit file and symbol revision links for analyses of how recorded contributions evolve. Code and experimental artifacts are described in \hyperref[sec:data]{Data Availability}.

To examine how histories explain the origin and contents of retained code, we ask \emph{RQ1: What does trajectory evidence add to static identification of retained helpers?} and \emph{RQ2: What do ghost scripts retain, and how does recorded agent language describe their role in the repair?}

\section{Static Analysis of Ghost Scripts}
\label{sec:static}
\label{sec:ghost}
Static analysis of a trajectory connects possible source-writing behavior with observed development events. A retained writer may be a required generator, an editing aid, or an unused proposal. Our bounded AST analysis propagates constant paths, file handles, source-read origins, and string/list transformations into write operations. It joins branches and approximates loops once. We apply it to retained Python files across their captured versions to identify construction candidates. Recorded invocations associate the executed helper version and its write destination with product changes in the same action. This connects a static finding to an observed development event. Following the affected code through later revisions then shows whether the helper's contribution survives or changes. This recovers construction evidence for attempts absent from the final patch.

The surviving helpers can themselves preserve these attempts. In Django task 13346, MiniMax M2.5 uses \code{/tmp/patch2.py} to insert a \code{KeyTransformIn} implementation, then revises the product while leaving the earlier class inside the helper as a string. An ordinary AST exposes the helper's file operations. Parsing its strings reveals the embedded implementation. We compare fingerprints of these definitions with product ASTs before and after the associated action. A match introduced by that action links the embedded definition to the product. Following it through later snapshots distinguishes implementations that remain current, are superseded, or return after a reversion. Source inspection separates replacement code from search patterns and unused proposals. Construction history and retained contents do not establish whether a helper can be removed. For final workspace $F$, helper $h$, and outcome vector $v_O$ of fixed task oracle $O$, task-level redundancy requires
\begin{equation}
v_O(F\setminus\{h\})=v_O(F).
\label{eq:redundancy}
\end{equation}
Both saved evaluations must be valid, complete, and passing under the same oracle, separating endpoint redundancy from usefulness during development.

\section{Exploratory Study}
\label{sec:study}
The archive contains 240 mini-SWE-agent 2.4.6 runs~\cite{mini}, with 20 SWE-bench Verified tasks per model across eight repositories. Runs used temperature 0.2 and official agent templates, with provider reasoning defaults uncontrolled. The saved census records 90 passing runs (37.5\%), 69 failures, and 81 invalid outcomes. Of the 90 passing endpoints, 88 passed two saved evaluations on fresh reconstructions with identical per-test outcomes under the same oracle. Two matplotlib environments failed during image unpacking before tests ran. The resulting cohort spans seven repositories. Captured new-source inventories occur in 56 runs and contain 1,662 Python file occurrences, including test-generated files. Helpers occur in 40 runs. Table~\ref{tab:population} reports the model and repository breakdowns. The connector archives commands, observations, and model records with Git-anchored snapshots, including captured untracked and temporary files.

Automated screening first nominated retained Python writers whose invocations coincided with tracked-source changes. Codex (Astra) assisted trajectory inspection. Two reviewers checked all 62 scripts against their trajectories and saved deletion evidence, agreeing on construction role and task redundancy. These cases informed prototype development, so reference recovery measures coverage of known cases. The AST discovery itself uses code and actions without consuming reference labels or deletion outcomes. This analysis and the ledger replay below use archived evidence, with no new agent runs or task-oracle executions.

\subsection{RQ1: Linking Candidates to Construction Events}
AST screening includes all 62 reference helpers among 65 source-writing candidates. As a simple baseline, filenames matching \code{patch*.py} or \code{fix*.py} select 63 occurrences, recover 57 references, and add six candidates with unknown redundancy. The five misses include \code{add_import.py} and \code{apply_fix.py}. History connects the AST candidates to the versions and source edits recorded when they ran. This matters when the surviving file differs from the script that performed the edit. Three candidates remain unresolved. Two invocations leave their targets unchanged, and one retained script is a copy of the version executed. Their deletion status is unknown.

\rqresult{RQ1}{AST screening finds 65 candidates. History corroborates all 62 reference helpers across 40 runs and links them to their construction actions. This adds construction evidence to retrospective reference recovery.}

\subsection{RQ2: Nature and Recorded Purpose of Ghost Scripts}
Embedded definitions in 25 helpers link to product code, with 20 current and five superseded implementations. All occur as string data, with no executable function or class definitions in the helper itself. The superseded implementations concern Django JSON lookups, pytest file-mode handling, and SymPy tuple printing. Two histories return to an earlier implementation after intervening revisions and are counted as current. The 37 unlinked helpers also write source, but lack a complete matched definition. Saved individual deletion trials preserve passing outcomes for all 62 helpers, and combined deletions preserve outcomes in the 40 affected runs across two checks. All 27 repository-local helpers appear as added files in the actual submitted patches, across 16 runs. The other 35 occupy external temporary paths and are absent from those patches. Temporary helpers document session activity and may matter when a workspace is reused. Effects on later tasks remain an evaluation question.

The submitted helpers expose a review question that passing tests alone leave unresolved. Linked histories distinguish the repair from the script used to construct it, grounding a cleanup decision in observed use and deletion evidence.

\paragraph{Recorded explanations and author verification}
\label{sec:language}
At the reference construction action, 48 helpers have narration or exposed reasoning and 14 do not. Quotations retain their action and source field. One author checked five purposively selected Codex-proposed readings against quotations and action/AST context, accepting all five. The cases cover current, superseded, and unlinked helpers, including missing direct language. These five readings illustrate how language qualifies the static evidence. DeepSeek V3.1 describes a failed \code{sed} command before creating Django's \code{fix_syntax.py}, and Qwen3-Coder-Next describes correcting SymPy tuple formatting. In Xarray, preceding narration supplies the intended dtype repair despite missing language at the helper action. In Sphinx, MiniMax M2.5 says ``Let me restore my fix'' before rerunning \code{/tmp/patch.py} during diagnosis. The helper was reused within the session, then redundant at the passing endpoint. The remaining language annotations are provisional.

\rqresult{RQ2}{Of 25 helpers with linked code, 20 retain current implementations and five retain superseded ones. Five author-reviewed language cases connect helper use to expressed repair decisions, including repeated reapplication during diagnosis.}

\subsection{Ledger Case Validation}
We replayed two preserved target-file histories through the released recorder and ledger, covering 12 changing actions in the Django and Sphinx cases above. A compatible graph seeded with real base-source AST spans enabled symbol attribution. The replay exercises ledger derivation and linking, with external indexing and live adapters outside its scope. One author checked three selected ledger interpretations against presented diffs and recorded explanations and agreed with all three. The ledger marked Django's earlier contribution revised, its replaced methods abandoned, and the replacement method survived. Sphinx's original fix survived despite three temporary reversions. Its diagnostic rollback was abandoned, although its normalized lines reappeared inside the final loop. This last case shows why ledger labels need source context. They indicate source differences, not the disappearance of equivalent text or behavior.

\section{Related Work}
Research on development rationale extracts explanations from commit messages~\cite{rationale} and design discussions in issue trackers~\cite{drminer}. Agent trajectories have also been analyzed to characterize repair strategies and success or failure~\cite{agentbehaviour}. \tracer{} connects these language records to file and symbol evolution. Repository-context approaches such as RepoCoder and Repoformer~\cite{repocoder,repoformer} motivate evaluating these links for later context selection. Git AI records agent authorship~\cite{gitai}. ChangeDistiller and GumTree analyze structural changes~\cite{changedistiller,gumtree,gumtree2024}, and clone genealogy follows related code across versions~\cite{genealogy,aigenealogy}. Our application traces source embedded as helper data into the product and its later revisions.

Provenance systems preserve relationships among artifacts and activities~\cite{prov,noworkflow,yesworkflow,reprozip}. We apply this perspective to captured coding-agent development. Delta debugging and program reduction identify removable inputs or code~\cite{dd,perses,chisel}, while TRIM minimizes agent-generated patches using trajectories~\cite{trim}. We use deletion evidence to establish task redundancy, then examine what retained helpers represent and how they were used.

\section{Threats to Validity}
The cohort selects passing, reproducible runs from one scaffold and a small task sample. Model differences are descriptive within this cohort, with provider reasoning settings uncontrolled. Human review confirms the 62 reference classifications but does not make prototype recovery independent. Capture is incomplete, particularly for temporary files. The Python analysis misses shell-only edits, other languages, and unsupported dynamic paths or calls. Compound actions limit causal attribution. Ledger labels depend on captured diffs and symbol baselines, with deletion-only edits and first-touch symbol attribution requiring separate inspection. Language and ledger cases were selected after inspection, and the proposed LLM readings may influence author judgments. Recorded explanations need not reflect faithful intent. The fixed task oracle establishes endpoint redundancy, not safety for future tasks.

\section{Future Plans}
\label{sec:future}
We will compare linked histories with final code and unlinked logs in review and agent continuation, measuring accuracy, task success, effort, and recording overhead. Ablations will separate the contribution of recorded language from code history. Repeated edits and reversions also offer evidence about development cost, provided useful diagnosis is distinguished from avoidable work. Security-focused studies could examine whether histories help reviewers locate the introduction and repair of security-relevant changes. We also plan an end-of-session cleanup stage in mini-SWE-agent that preserves the development record while validating proposed removals. Evaluation will include indispensable helpers and independently labeled sessions, measuring incorrect removal, task success, and overhead.

\section{Conclusion}
Development histories give SE tools and natural-language analysis a shared record of how code came to be. \tracer{} preserves this record for inspection and reuse. Our exploratory ghost-script study shows how AST and history analysis can identify construction roles and distinguish retained implementations that remain current from those later revised. Five author-reviewed language cases connect observed changes to expressed repair decisions, including the reuse of a helper that was redundant at the endpoint. Together, these findings support studying provenance through both code evolution and its recorded context. Evaluating how this evidence helps people and agents review edits, continue repairs, and make maintenance decisions is a promising direction for SE research.
