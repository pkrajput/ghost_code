\title{Development Histories as Software Evidence}
\author{}
\begin{document}
\maketitle

\begin{abstract}
Software development produces explanations, actions, and intermediate code whose relationships can be lost after a task ends. Coding-agent sessions offer an opportunity to preserve this process as reusable software evidence. We introduce \tracer{} (Trace-based Runtime Analysis for Code Evolution Review), an agent-independent architecture that links recorded reasoning and actions to file and symbol changes, preserves revisions, and derives a decision ledger. Such histories bring natural-language context together with code evolution for human inspection, subsequent agents, and software analysis. We investigate one use by combining static analysis of mini-SWE-agent trajectories on SWE-bench with a qualitative review of recorded agent explanations. We trace the creation and use of retained helper scripts before examining their embedded source code. The analysis recovers 62 previously validated helpers whose removal preserved passing task outcomes. Among the embedded implementations linked to product code, some match its final version and others have been superseded. An initial author review of the recorded explanations connects stated repair decisions to the observed code revisions. This case study shows how linking language with code evolution clarifies the role and contents of artifacts left by an agent.
\end{abstract}
\begin{IEEEkeywords}
development history, coding agents, software provenance, static analysis
\end{IEEEkeywords}

\section{Introduction}
Understanding a software change requires context. Source versions preserve edits, while explanations and observations may be dispersed across discussions, logs, and temporary workspaces. Intermediate attempts can disappear before a commit. Later reviewers and agents must reconstruct their relationships. Preserving those relationships during development would make the process available for inspection and reuse.

Coding agents offer a practical opportunity to capture this context at each development action. Systems such as SWE-agent and OpenHands edit and execute code through recorded interfaces~\cite{sweagent,openhands,codeact}. Natural-language records describe expressed rationale, including exposed chain of thought (CoT) where available. Commands, observations, and code versions document the associated activity. Linking these records lets an analyst inspect an explanation alongside changes recorded in the same step. We propose treating linked development histories as reusable software evidence. \tracer{}: \emph{Trace-based Runtime Analysis for Code Evolution Review}, connects steps to file and symbol changes through Git diffs, preserves revisions, and derives a decision ledger. Its adapter contract separates recording from particular agents and analyses. The aim is to retain context before its recovery becomes an archaeology task. Available reasoning is part of this evidence, without assuming access to hidden thought or treating recorded explanations as faithful intent.

Linked histories could help developers review earlier repair attempts, subsequent agents recover prior observations, and program analyses explain artifacts left in a workspace. We investigate this opportunity through helper scripts that survive an agent session. We first use abstract syntax trees (ASTs) and recorded actions to identify scripts used to rewrite product source. Saved deletion trials then establish which helpers can be removed while preserving the fixed passing task-oracle outcome. We call these task-redundant helpers \emph{ghost scripts}. The label concerns the final workspace; a helper may have been used repeatedly while developing the fix. Task-level redundancy alone does not explain what these scripts contributed to the repair or what information they still contain. We therefore examine their trajectories and embedded code alongside the agent's recorded explanations. Across passing mini-SWE-agent runs on SWE-bench~\cite{swebench}, the analysis recovers 62 reference helpers with deletion evidence. Some store product implementations as strings, preserving either the final fix or an earlier attempt that was subsequently revised. Others perform edits for which no complete embedded definition can be linked to the product. Recorded language can help explain why an agent created or revised a helper, while leaving its reason for retaining the file unstated. We complement the static findings with LLM-assisted interpretation of this language and author verification of illustrative cases. This connects what a script did, what the agent said about the associated action, and what remained after the repair. The resulting evidence allows us to study ghost scripts as records of development, including the possibility that their contents could inform later fixes.

\subsection{Linking Reasoning to Symbol Changes}
The structural index builds on \code{codebase-memory-mcp} project~\cite{codebasememory}. \tracer{} reads its code graph, including qualified symbol names, source spans, and relationships. For each Git revision range, changed line ranges are mapped to the innermost overlapping symbols. Live AST extraction resolves new symbols and changed spans; re-indexing and reconciliation update their graph identities. Unresolved ranges fall back to file-level links. These links attach the step's prompt and recorded reasoning to its affected code. Provenance tags distinguish narration, tool-call thoughts, exposed chain of thought (CoT), and provider summaries when available. 

\subsection{Revisions and the Decision Ledger}
The Git-backed driver checkpoints development steps, retaining intermediate attempts. A separate SQLite trace store holds steps, node links, signatures, and symbol co-change records. Per-version snapshots preserve structural changes. Development lineages retain fork points and merge visibility, while historical records remain inspectable after later edits. Optional reasoning embeddings support CoT search. The decision ledger is derived from recorded revisions without an LLM. For each step, it compares added line text with session-end removals through two Git diffs. Normalized-text overlap yields \emph{survived}, \emph{revised}, or \emph{abandoned} entries. Symbol entries additionally check whether linked definitions remain. Error observations followed by further actions generate \emph{error\_retry} entries. Records retain abandoned content and heuristic links to later surviving steps on the same symbol or file. These are reproducible development summaries, not correctness verdicts or ghost labels.

\subsection{Reusable History and Analysis Interfaces}
File/symbol history queries, version navigation, and review bundles expose diffs with their recorded reasoning and ledger entries. The panel connects code structure to the step timeline. The intended release separates this general \tracer{} tool from agent connectors and study-specific analyses. 

\section{Static Analysis of Recorded Code Trajectories}
\label{sec:static}
We analyze captured trajectories offline, identifying construction helpers and characterizing their retained code (Section~\ref{sec:ghost}). The application uses the mini-SWE-agent integration.

\subsection{Connecting mini-SWE-agent}
The study adapter records commands, exit codes, raw and model-visible output, and model requests/responses. Git-anchored, content-addressed snapshots preserve initial and post-action workspaces, including untracked files and bounded temporary-file captures. It exports the \tracer{} step shape using snapshot identifiers instead of per-action Git commits. The AST analysis consumes these records directly, helper links and definition currency are derived below. Recorded model responses provide the language evidence for the qualitative review. The general decision ledger is not evaluated in this study.

\subsection{Recovering Source-Writing Behavior}
For each retained Python path, we analyze every captured version. Abstract values track constant paths, file handles, read origins, and transformations. Assignments propagate values through \code{open}, \code{pathlib} operations, string/regular-expression replacements, and selected list mutations. A source-writing candidate requires a resolved Python destination and records the written value's origins.

\section{Studying Ghost Scripts}
\label{sec:ghost}
\subsection{What Survives an Agent Session?}
In \code{django__django-13346}, MiniMax M2.5 invokes \code{/tmp/patch2.py} to write \code{KeyTransformIn} into \code{django/db/models/fields/json.py}. Later actions replace it. The passing endpoint uses \code{batch_process_rhs}, while the script's \code{new_class} string retains the earlier \code{resolve_expression_parameter} and \code{process_rhs} methods.

The helper's ordinary AST exposes writing operations but no executable definitions. Parsing its strings and linking them to product versions identifies the retained construction attempt.

We distinguish three properties. \emph{Construction role} associates a surviving helper with a source-writing action. \emph{Currency} describes whether a linked implementation matches the endpoint, has been superseded, or cannot be resolved. \emph{Task-level redundancy} requires deletion evidence. For final workspace $F$, helper $h$, and the outcome vector $v_O$ of fixed oracle $O$, the latter is
\begin{equation}
v_O(F\setminus\{h\})=v_O(F).
\label{eq:redundancy}
\end{equation}
Both evaluations must be valid and complete under the same oracle. AST similarity or a missing caller cannot establish this equality, which also leaves future maintenance value unresolved.

\subsection{Following Embedded Implementations}
Characterization extracts string literals containing source definitions. A statement wrapper permits indented fragments without altering multiline string values. Location-free AST fingerprints preserve names, literals, operators, decorators, and docstrings in function and class definitions.

Let $H$ be the AST fingerprint and $D_e(f,q)$ the definition at file $f$ and qualified name $q$ in state $e$. An embedded payload $p$ is a produced-version candidate when
\begin{equation}
H(p)=H(D_{e^+}(f,q)),\qquad
H(p)\ne H(D_{e^-}(f,q)),
\label{eq:link}
\end{equation}
where $e^-$ and $e^+$ denote the action's before/after states. The payload matches a definition observed after the action but absent or different before it. Known absence has a distinguished fingerprint; unavailable source is not absence. Whole-class matches subsume contained methods. Argument-use tags and source inspection distinguish replacement payloads from search patterns and unused literals.

We follow definitions matched by Equation~\ref{eq:link} through later snapshots. Equal endpoint fingerprints indicate current correspondence; a unique different definition indicates supersession. Missing or renamed definitions, duplicates, and parse failures remain unresolved. Tracking definitions preserves reversions without confusing enclosing-file edits with definition changes.

\section{Exploratory Study}
\label{sec:study}
We ask \emph{RQ1: Can static analysis of agent trajectories identify retained construction helpers? RQ2: What do ghost scripts retain, and how does recorded agent language describe their role in the repair?}

\paragraph{Population}
The archive contains 240 runs using mini-SWE-agent 2.4.6~\cite{mini}, with 12 model configurations on 20 SWE-bench Verified tasks across eight repositories. The models are DeepSeek V3-0324, V3.1-Terminus, V3.2; MiniMax M2, M2.1, M2.5; Qwen3-Coder-Next, Qwen3.5-35B-A3B, Qwen3.5-122B-A10B; and Llama 3.1-70B-Instruct, 3.3-70B-Instruct, 4-Maverick. All used temperature 0.2 and the official agent templates; provider reasoning defaults were not controlled.

The cohort comprises 88 endpoints with matching passing check vectors across two saved evaluations. Ten configurations contribute; Llama 3.1 and Maverick contribute none. The exclusions are 149 recorded nonpassing runs, one invalid endpoint, and two unavailable replay environments. Exact model IDs and per-model counts accompany the artifact.

The full captured inventory contains 1,695 $(\text{run},\text{path})$ occurrences across 56 eligible runs, including 1,411 pytest-temporary artifacts. The other 32 runs contribute no entry. Python analysis covers 1,662 files; 33 are unsupported. Eleven Python endpoints fail parsing, all test-generated.

\paragraph{Reference and validation}
Discovery discards prior nomination, origin, and deletion labels. We subsequently compare with 62 frozen positive references and join saved deletion results by run, path, and hash. These examples informed development, including invocation refinements after reference misses. The comparison measures retrospective recovery, not population precision or recall.

No new agent runs or subject executions were performed. Hash and snapshot checks plus 26 local tests cover analysis boundaries and a synthetic archive without nomination inputs. Source inspections were Codex-assisted. The language review below adds author verification of selected interpretations; it is separate from the static detector validation.

\subsection{RQ1: Identification and Historical Evidence}
AST analysis finds 65 source-writing candidates. History corroborates 62 files across 40 runs: 27 repository files and 35 external temporary files (Table~\ref{tab:discovery}). These recover every reference helper and its nominated edit event. The AST-only stage already includes all 62 references; history adds evidence about actual construction intervals rather than increasing reference recall.

\subsection{RQ2: Nature of Retained Scripts}
Characterization uses the recovered reference edit events and previously audited comparisons. Twenty-seven helpers contain parseable embedded definitions. Matching links 25 to product definitions across 20 runs and eight tasks. Of 37 unlinked helpers, 35 lack complete parseable definitions, one contains a partial replacement, and one an unused proposed class. Writing analysis still detects them.

Three of 28 raw matches are excluded as pre-existing search patterns or unchanged methods. The 25 primary links use 18 string replacements, four regular-expression replacements, two list insertions, and one list-slice replacement. None of these helpers has executable function/class definitions; their implementations exist in string data.

\subsection{Recorded Explanations and Human Verification}
\label{sec:language}
We link original assistant messages to helper actions through tool-call identifiers and retain surrounding revision statements. Quotations preserve their event and source field, distinguishing provider-exposed reasoning from assistant narration. At the reference construction action, 48 of the 62 helpers have nonblank recorded language; 14 do not. Surrounding text remains contextual evidence rather than a direct explanation of that action.

Codex proposed interpretations of expressed purpose and any explicit retention rationale for all helpers. One author checked five purposively selected case interpretations against presented quotations and action/AST context, accepting all five. Selection covered current, superseded, and unlinked helpers, including a case without direct language. The cohort-wide annotations remain provisional; author verification is restricted to these five presented case readings. This author check establishes support for the presented readings, without estimating annotation accuracy or reasoning faithfulness.

The reviewed cases illustrate different information supplied by language. In Django 13346, DeepSeek V3.1 explains that a \code{sed} command failed before creating \code{fix_syntax.py}, providing a reason for changing the editing method. MiniMax M2.5's Django reasoning and Qwen3-Coder-Next's SymPy narration describe problems corrected in later implementations. In Sphinx 8056, MiniMax M2.5 says ``Let me restore my fix'' before rerunning \code{/tmp/patch.py} during diagnosis. The helper was reused within the session even though endpoint deletion preserved passing outcomes. For Xarray 7393, preceding narration explains a dtype repair, while the helper's construction action itself has no recorded explanation. These readings contextualize the scripts' use without establishing why they remained after the task or whether they would help future repairs.

\section{Related Work}
RepoCoder and Repoformer retrieve repository context~\cite{repocoder,repoformer}. Construction annotations could inform such retrieval. Git AI records agent authorship through checkpoints and Git metadata~\cite{gitai}; here we examine retained artifacts' roles and relationships to produced code.

ChangeDistiller and GumTree extract changes through tree differencing~\cite{changedistiller,gumtree,gumtree2024}. Clone genealogy follows related fragments across versions~\cite{genealogy}, including in human--agent development~\cite{aigenealogy}. Our AST fingerprints connect source stored as a helper's data to a product definition and follow it through the repair history.

Provenance research distinguishes entities, activities, and derivations~\cite{prov}. noWorkflow combines AST analysis and runtime information~\cite{noworkflow}, YesWorkflow exposes script workflows through annotations~\cite{yesworkflow}, and ReproZip captures execution dependencies~\cite{reprozip}. Our analysis uses existing action snapshots to interpret retained construction artifacts without instrumenting or rerunning them.

Delta debugging isolates relevant input or changes~\cite{dd}, Perses uses syntax to guide reduction~\cite{perses}, and Chisel addresses program debloating~\cite{chisel}. TRIM minimizes agent-generated patches using trajectories and reports removal of scratch scripts~\cite{trim}. Here, construction provenance describes a helper's writing role and represented version. Separate deletion checks validate redundancy; automatic removal remains future work.

\section{Threats to Validity}
The retrospective study conditions on passing, reconstructable runs from one scaffold and a small task sample. Repeated tasks and models make files non-independent. Recovering 62 development examples does not establish general accuracy; unselected files lack independent non-helper labels.

The inventory covers captured new files, not every repository symbol; temporary capture is incomplete. Results concern workspaces, including external temporary files, rather than necessarily submitted patches. Bounded AST and shell analyses miss indirect invocation, reflection, complex APIs, and dynamic paths. Snapshot intervals can contain multiple operations or conceal changes undone within an action. Exact embedded matching misses transformed fragments, while named-definition tracking leaves moves and duplicates unresolved. Assistant inspection and unit tests establish inspectability and internal consistency. The five language cases were selected after inspecting the results, and author judgments may be influenced by the proposed LLM interpretation; this is not an independent inter-rater study. Recorded explanations need not reflect faithful intent; an unstated retention rationale remains unknown. Finally, the same task oracle defines eligibility and redundancy; passing deletion checks does not establish general removal safety or future usefulness.

\section{Future Plans}
\label{sec:future}
We will release \tracer{} with separate adapter and analysis packages, then evaluate a frozen helper detector on independently labeled sessions. Maintained generators should be included when comparing precision, recall, and abstention against AST-only screening. Controlled studies should compare review accuracy and agent task success using linked histories, final code, and unlinked logs. Ablations should isolate recorded reasoning's contribution.

\paragraph{Development efficiency}
Repeated AST states and unchanged invocation targets nominate work for inspection. Recorded duration and usage could quantify their cost. Independent labels must distinguish avoidable work from useful exploration and verification.

\paragraph{Security analysis}
History could contextualize security-relevant changes, such as removing input validation. Independently adjudicated cases should compare reviewers' localization of introducing and corrective edits against final diffs and unlinked trajectories. Vulnerability and exploitability require separate evidence.

\paragraph{Validated cleanup in mini-SWE-agent}
An end-of-session stage could nominate helpers, archive their history, and remove them under a retention policy with validation. Evaluation must include indispensable helpers and measure incorrect removal, task success, and overhead. These interventions remain unevaluated.

\section{Conclusion}
\tracer{} preserves development as linked evidence for later inspection and reuse. Our static analysis recovers 62 reference helpers with saved redundancy evidence and distinguishes current from superseded implementations. The study connects construction history with recorded explanations of repair activity. Benefits to people or subsequent agents remain open research questions.
