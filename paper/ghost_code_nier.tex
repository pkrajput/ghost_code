\title{Development Histories as Software Evidence}
\author{}
\begin{document}
\maketitle

\begin{abstract}
Software development produces explanations, actions, and intermediate code whose relationships can be lost after a task ends. Coding-agent sessions offer an opportunity to preserve this process as reusable software evidence. We introduce \tracer{} (Trace-based Runtime Analysis for Code Evolution Review), an agent-independent architecture that links recorded reasoning and actions to file and symbol changes, preserves revisions, and derives a decision ledger. Such histories bring natural-language context together with code evolution for human inspection, subsequent agents, and software analysis. We investigate one use by combining static analysis of mini-SWE-agent trajectories on SWE-bench with a qualitative review of recorded agent explanations. We trace the creation and use of retained helper scripts before examining their embedded source code. The analysis recovers 62 previously validated helpers whose removal preserved passing task outcomes. Among the embedded implementations linked to product code, some match its final version and others have been superseded. An initial author review of the recorded explanations connects stated repair decisions to the observed code revisions. This case study shows how linking language with code evolution clarifies the role and contents of artifacts left by an agent.
\end{abstract}
\begin{IEEEkeywords}
development history, coding agents, software provenance, static analysis
\end{IEEEkeywords}

\section{Introduction}
Understanding a software change requires context. Source versions preserve edits, while explanations and observations may be dispersed across discussions, logs, and temporary workspaces. Intermediate attempts can disappear before a commit. Later reviewers and agents must reconstruct their relationships. Preserving those relationships during development would make the process available for inspection and reuse.

Coding agents offer a practical opportunity to capture this context at each development action. Systems such as SWE-agent and OpenHands edit and execute code through recorded interfaces~\cite{sweagent,openhands,codeact}. Natural-language records describe expressed rationale, including exposed chain of thought (CoT) where available. Commands, observations, and code versions document the associated activity. Linking these records lets an analyst inspect an explanation alongside changes recorded in the same step. We propose treating linked development histories as reusable software evidence. \tracer{}: \emph{Trace-based Runtime Analysis for Code Evolution Review}, connects steps to file and symbol changes through Git diffs, preserves revisions, and derives a decision ledger. Its adapter contract separates recording from particular agents and analyses. The aim is to retain context before its recovery becomes an archaeology task. Available reasoning is part of this evidence, without assuming access to hidden thought or treating recorded explanations as faithful intent.

Linked histories could help developers review earlier repair attempts, subsequent agents recover prior observations, and program analyses explain artifacts left in a workspace. We investigate this opportunity through helper scripts that survive an agent session. We first use abstract syntax trees (ASTs) and recorded actions to identify scripts used to rewrite product source. Saved deletion trials then establish which helpers can be removed while preserving the fixed passing task-oracle outcome. We call these task-redundant helpers \emph{ghost scripts}. The label concerns the final workspace, even when a helper was used repeatedly while developing the fix. Task-level redundancy alone does not explain what these scripts contributed to the repair or what information they still contain. We therefore examine their trajectories and embedded code alongside the agent's recorded explanations. Across passing mini-SWE-agent runs on SWE-bench~\cite{swebench}, the analysis recovers 62 reference helpers with deletion evidence. Some store product implementations as strings, preserving either the final fix or an earlier attempt that was subsequently revised. Others perform edits for which no complete embedded definition can be linked to the product. Recorded language can help explain why an agent created or revised a helper, while leaving its reason for retaining the file unstated. We complement the static findings with LLM-assisted interpretation of this language and author verification of illustrative cases. This connects what a script did, what the agent said about the associated action, and what remained after the repair. The resulting evidence allows us to study ghost scripts as records of development, including the possibility that their contents could inform later fixes.

We contribute \tracer{}, an architecture for preserving linked development histories, and an AST analysis that uses those histories to identify construction helpers and follow their embedded implementations. Our exploratory SWE-bench study combines retrospective validation with five author-reviewed language cases to examine what surviving scripts represent. Together, these contributions make the origin of retained code, its revisions, and the agent's expressed reasons available for inspection.

\section{TRACER Architecture}
\label{sec:tracer}

\begin{figure*}[t]
\centering
\includegraphics[width=\textwidth]{figures/tracer_ghost_script_overview.pdf}
\caption{\tracer{} links recorded explanations, actions, and code revisions into a reusable development history (top). The ghost-script application follows helper trajectories and embedded code, joins saved deletion outcomes, and checks selected language interpretations with an author (bottom).}
\label{fig:overview}
\end{figure*}
\tracer{} preserves actions, code revisions, and recorded explanations as linked development histories (Figure~\ref{fig:overview}). Its architecture separates agent adapters, a recording core, and analysis modules. Each step associates the prompt and available reasoning with the action's before/after versions. The structural index comes from \code{codebase-memory-mcp}~\cite{codebasememory}, which supplies symbol names, source spans, and relationships. Git diffs locate edits, and AST information maps them to functions and classes, with file-level links when a symbol cannot be resolved. Analysts can follow a symbol's revisions alongside the explanations recorded at each step. Narration, tool-call thoughts, exposed CoT, and provider summaries retain their source fields.

The Git-backed recorder preserves intermediate attempts, including code later revised or abandoned. A decision ledger derives whether introduced code survives, changes, or disappears without an LLM. Its entries describe code evolution, not correctness. Branch histories retain alternative attempts, and optional embeddings support searches over recorded reasoning. File and symbol queries, version navigation, and review bundles expose this history through a timeline. The tool supports OpenHands and human-edit interfaces alongside the mini-SWE-agent connector used here. These interfaces let subsequent agents and SE analyses inspect how an artifact was produced and what happened to it later. Code and experimental artifacts are described in \hyperref[sec:data]{Data Availability}.

To examine how histories explain the origin and contents of retained code, we ask \emph{RQ1: Can static analysis of agent trajectories identify retained construction helpers?} and \emph{RQ2: What do ghost scripts retain, and how does recorded agent language describe their role in the repair?}

\section{Static Analysis of Ghost Scripts}
\label{sec:static}
\label{sec:ghost}
Static analysis of a development trajectory can connect a file's behavior to its role in producing other code. A script that writes source may be an editing aid, a required generator, or an unused proposal. Its contents alone do not establish which role it played in a repair. We analyze the ASTs of retained Python files across their captured versions, following source reads, transformations, and writes to identify construction candidates. Recorded invocations associate the executed helper version and its write destination with product changes in the same action. This connects a static finding to an observed development event. Following the affected code through later revisions then shows whether the helper's contribution survives or changes. Such associations give SE analyses evidence about how code came to be, including intermediate attempts absent from the final patch.

The surviving helpers can themselves preserve these attempts. In Django task 13346, MiniMax M2.5 uses \code{/tmp/patch2.py} to insert a \code{KeyTransformIn} implementation, then revises the product while leaving the earlier class inside the helper as a string. An ordinary AST exposes the helper's file operations. Parsing its strings reveals the embedded implementation. We compare fingerprints of these definitions with product ASTs before and after the associated action. A match introduced by that action links the embedded definition to the product. Following it through later snapshots distinguishes implementations that remain current, are superseded, or return after a reversion. Source inspection separates replacement code from search patterns and unused proposals. Unresolved matches remain unknown. Construction history and retained contents do not establish whether a helper can be removed. For final workspace $F$, helper $h$, and outcome vector $v_O$ of fixed task oracle $O$, task-level redundancy requires
\begin{equation}
v_O(F\setminus\{h\})=v_O(F),
\label{eq:redundancy}
\end{equation}
with valid, complete, passing evaluations under the same oracle. We join saved deletion evidence to establish this endpoint property separately from the helper's usefulness during development.

\section{Exploratory Study}
\label{sec:study}
The archive contains 240 mini-SWE-agent 2.4.6 runs~\cite{mini} using 12 model configurations on 20 SWE-bench Verified tasks across eight repositories. The models are DeepSeek (V3-0324, V3.1-Terminus, V3.2), MiniMax (M2, M2.1, M2.5), Qwen (Qwen3-Coder-Next, Qwen3.5-35B-A3B, Qwen3.5-122B-A10B), and Llama (3.1-70B-Instruct, 3.3-70B-Instruct, 4-Maverick). Runs used temperature 0.2 and official agent templates, with provider reasoning defaults uncontrolled. The connector records commands, observations, and model requests/responses alongside Git-anchored initial and post-action snapshots, including captured untracked and temporary files. The general decision ledger is outside this evaluation. We study 88 reconstructable endpoints with matching passing outcomes across two saved evaluations. The inventory contains 1,662 Python file occurrences across 56 of these runs, including files generated by tests. The remaining runs contribute no new-file entry.

Discovery uses recorded code and actions before comparison with 62 frozen reference helpers and their saved deletion results. These examples informed prototype development, so recovery is a retrospective check. No new agent runs or subject executions were performed. Analysis-script development and source inspection were Codex-assisted, with author verification of selected language interpretations.

\subsection{RQ1: Identification and Historical Evidence}
AST screening includes all 62 reference helpers among 65 source-writing candidates. History corroborates their nominated edit events and connects each helper to the version used during construction. This matters when the surviving file differs from the script that performed the edit. Three candidates remain unresolved. Two invocations leave their targets unchanged, and one retained script is a copy of the version executed. Their deletion status is unknown.

\rqresult{RQ1}{AST screening finds 65 candidates. History corroborates all 62 reference helpers across 40 runs and links them to their construction actions. Recovery is retrospective.}

\subsection{RQ2: Nature and Recorded Purpose of Ghost Scripts}
Embedded definitions in 25 helpers link to product code (Table~\ref{tab:currency}). All occur as string data, with no executable function or class definitions in the helper itself. The superseded implementations concern Django JSON lookups, pytest file-mode handling, and SymPy tuple printing. Two other histories return to an earlier implementation after intervening revisions. The 37 unlinked helpers also write source, but lack a complete matched definition. Saved individual deletion trials preserve passing outcomes for all 62 helpers, and combined deletions preserve outcomes in the 40 affected runs across two checks. Task redundancy therefore spans helpers with current, superseded, and unlinked contents.

\paragraph{Recorded explanations and author verification}
\label{sec:language}
At the reference construction action, 48 helpers have nonblank narration or exposed reasoning and 14 do not. We link quotations to actions and retain their source fields, distinguishing direct statements from surrounding context. Codex proposed interpretations of expressed purpose and explicit retention rationale. One author checked five purposively selected readings against presented quotations and action/AST context, accepting all five. These cases span current, superseded, and unlinked helpers and include missing direct language. Cohort-wide annotations remain provisional. In Django, DeepSeek V3.1 describes a failed \code{sed} command before creating \code{fix_syntax.py}. MiniMax M2.5's Django reasoning and Qwen3-Coder-Next's SymPy narration explain revisions to earlier attempts. In Xarray, preceding narration describes the intended dtype repair despite the absence of language at the helper action. In Sphinx, MiniMax M2.5 says ``Let me restore my fix'' before rerunning \code{/tmp/patch.py} during diagnosis. The helper was reused within the session, then redundant at the passing endpoint. The reviewed language explains its use, but does not establish why it was retained or whether it would help a future task.

\rqresult{RQ2}{Of 25 helpers with linked code, 20 retain current implementations and five retain superseded ones. Five author-reviewed language cases connect helper use to expressed repair decisions, including repeated reapplication during diagnosis.}

\section{Related Work}
Repository-context approaches such as RepoCoder and Repoformer~\cite{repocoder,repoformer} motivate studying whether construction history helps select useful context. Git AI records agent authorship~\cite{gitai}. \tracer{} connects actions and explanations to code evolution so that retained artifacts can be studied through their development roles. ChangeDistiller and GumTree analyze structural changes~\cite{changedistiller,gumtree,gumtree2024}, while clone genealogy follows related code across versions~\cite{genealogy,aigenealogy}. Our application links source embedded as helper data to product definitions and follows them through a repair.

Provenance systems preserve relationships among artifacts and activities~\cite{prov,noworkflow,yesworkflow,reprozip}. We apply this perspective to coding-agent development, where actions, intermediate code, and explanations can be captured together. Delta debugging and program reduction identify removable inputs or code~\cite{dd,perses,chisel}, and TRIM minimizes agent-generated patches using trajectories~\cite{trim}. We examine what surviving helpers represent and how they were used, with deletion evidence establishing task redundancy separately.

\section{Threats to Validity}
The study covers passing, reconstructable runs from one scaffold and a small task sample. Examples informed development, so recovery does not establish general detector accuracy. Captured files, especially temporary files, are incomplete and need not appear in the submitted patch. Bounded static analysis can miss dynamic behavior, and compound actions limit causal attribution. Unresolved definition links remain unknown. The five language cases were selected after inspection, and author judgments may be influenced by the proposed LLM readings. Recorded explanations need not reflect faithful intent. The same fixed oracle defines passing outcomes and redundancy, so deletion success does not establish safety for future tasks.

\section{Future Plans}
\label{sec:future}
We will compare linked histories with final code and unlinked logs in code review and agent task continuation, measuring review accuracy, task success, and effort. Ablations will separate the contribution of recorded language from code history. Repeated edits and reversions also offer evidence about development cost, provided useful diagnosis is distinguished from avoidable work. Security-focused studies could examine whether histories help reviewers locate the introduction and repair of security-relevant changes. We also plan an end-of-session cleanup stage in mini-SWE-agent that preserves the development record while validating proposed removals. Evaluation will include indispensable helpers and independently labeled sessions, measuring incorrect removal, task success, and overhead.

\section{Conclusion}
Development histories give SE tools and natural-language analysis a shared record of how code came to be. \tracer{} preserves this record for inspection and reuse. Our exploratory ghost-script study shows how AST and history analysis can identify construction roles and distinguish retained implementations that remain current from those later revised. Five author-reviewed language cases connect observed changes to expressed repair decisions, including the reuse of a helper that was redundant at the endpoint. Together, these findings support studying provenance through both code evolution and its recorded context. Evaluating how this evidence helps people and agents review edits, continue repairs, and make maintenance decisions is a promising direction for SE research.
